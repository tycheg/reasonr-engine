## E1

1. **Ports** (`engine/port`): `Executor`, `UnitStore`, `Reader`, `TimerSource`, `EffectSource`, `ProjectionStore`, `EventSink`, `Publisher`, `IntegrationTransport`, `NotificationHub`, `KeyStore`, `Listener`, `Codec`, `Authenticator`, `Metrics`, `Tracer`, `Clock`, lifecycle interfaces; the types `Tenant`, `Position`, `Unit`, `CommittedUnit`, `CommandResult`, `LeasedTimer`, `Capabilities`, `UniqueViolation`; the errors `ErrConflict`, `ErrTimerGone`, `ErrDuplicateKey`, `ErrNotReady`, `ErrUnknownTenant`, `ErrUnauthenticated`, `ErrPermanent`. The transport and telemetry ports are declared; their implementations come in E2.
2. **The kernel** (`engine/kernel`) moved out of `engine/memory` and implements `port.Executor`:
   - the programs of data tenants (`Programs`, also `port.Catalog`): data tenant → interpreter, many tenants may use one program;
   - the `Env` router: entities and synchronous projections are read from the main store, asynchronous ones (`Config.Async` by projection name) from their own `ProjectionStore`; operations on asynchronous projections go to the outbox, on synchronous ones they are applied on commit;
   - the loop "execute → commit → retry on `ErrConflict`" (16 attempts), the uniqueness error from `IndexInfo.Error`;
   - the idempotency key: the response is looked up before execution and stored with the unit of work; a race of two calls with one key is resolved by `ErrDuplicateKey` and reading the stored response;
   - notifications: without `to` — to the initiator; to the initiator — in `CommandResult`, to other actors — into `NotificationHub` after commit; a hub error is only logged;
   - timers (`Fire`): the command is committed together with deleting the timer row; a business error deletes the timer; a failure — a retry after 1, 2, 4… s, after 10 failures the timer is dead; if the timer is already gone, the answer is `nil`;
   - a query with `after` waits for the model's asynchronous stores up to `ConsistencyWait` (2 s), otherwise `ErrNotReady`;
   - manual migrations (a unit of work is a command call), the determinism check, metrics of commands, conflicts and timers.
3. **Memory as adapters** (`engine/memory`): `Store` — `UnitStore`, `ProjectionStore`, `TimerSource`, `EffectSource` with data separated by tenant and schemas from the catalog; `Hub` — `NotificationHub` (with a journal for the test driver); `Events` — `EventSink`; `Clock` — a clock per tenant. `memory.Engine` is the kernel with these adapters and the previous API for `reasonr test` (`Execute`, `Query`, `Advance`, `Migrate`, `Deliveries`); `Execute` and `Advance` now return `port.CommandResult`.
4. **Conformance tests** (`engine/conformance`): `RunUnitStore` — 18 checks (loading and versions, sequence, a conflict and the retry limit, uniqueness and releasing a value, forget and its outbox record, migrations, search with every condition and page, idempotency of an accepted and a rejected command, tenant isolation, capabilities, timers in order, a lease, retry and dead timers, a timer that is already gone, selection by tenant, outbox and positions, `Wait`, asynchronous projection operations); `RunProjectionStore` — applying, a partial upsert, deleting, idempotency by position, `Applied`, search, tenants; `RunHub` — delivery to every subscription of the recipient and only to them, tenants, `Close`, context cancellation. The model is embedded in the package (`testdata/store`), so the suite can be wired from any adapter module. Checked with mutations of the memory adapter: removing the idempotency of `Apply` and removing the timer lease are caught.
5. **Kernel tests**: `after` and `ErrNotReady`, waiting for delivery during a query, notifications in the response and in the hub, a timer with a business error, a failure with a retry, a dead timer and reviving it, a race of idempotency keys, an unknown tenant.
6. **The canonical JSON** (`runtime/jsonv`): an encoder and a decoder by schema without reflection, our own JSON scanner; errors `*jsonv.Error` with a path (`p.x`, `l[1]`, `m[0][1]`) — for the `invalidArgument` response in E2. Tests: the exact form of every kind, what is accepted on input beyond the canonical form, errors with a path, a round-trip test on 500 random records with every kind of value; the fuzz tests `FuzzRoundTrip` and `FuzzDecode` are in `make fuzz`.
7. **Checks:** `reasonr test` and the example tests (taxi, `acme`, bank, the "broken" ones with expected files) pass on the kernel without report changes; `FuzzEngine` works through the kernel (2.3 million runs a minute without failures); `go test -race` of the engine packages is clean. The VM still does not allocate; all taxi tests on the in-memory engine take 1.6 ms (was 1.3 ms; the kernel, the hub and the outbox were added; the goal is < 50 ms).

## E2

1. **The HTTP API** (`edge/httpapi`) on top of `port.Executor`: commands and queries by schema in the canonical JSON, the response codes of §8.1, notifications to the initiator in the response body, `Idempotency-Key`, `after`, `invalidArgument` with a path and a rule (`type`, `required`, `range`, `encoding`, `check`, `unknown`, `count`), a failure — 500 with an incident id, the details (the place in the model, the stack) only in the log.
2. **Notifications to other actors**: WebSocket (our own RFC 6455 implementation: text frames, ping/pong, close, checking the mask and the sizes of client frames) and long polling (`/api/poll?cursor=…&wait=…`, a buffer per actor — 100 notifications, 60 s; the subscription closes after 60 s without polls). Only actors get notifications.
3. **Authentication** (`edge/auth`): JWT HS256, RS256, ES256; keys — a secret, PEM or JWKS with a 10-minute cache, reread on an unknown `kid` at most once every 30 s; claims → tenant, actor type and id, roles; API keys (stored as SHA-256); the test scheme `Test` only with `--test`.
4. **OpenAPI 3.1** of the caller's tenant model: the paths of public commands and queries, schemas of enums, value objects and records, shared responses. The taxi (base and `acme`) and bank descriptions pass `npx @redocly/cli lint` (`REASONR_OPENAPI_DIR=… go test ./edge/httpapi -run TestOpenAPIDump`); three warnings remain — no `license`.
5. **Telemetry** (`telemetry`): `slog` text/JSON with a level; `port.Metrics` in the Prometheus text format (`/metrics` on the HTTP transport or on a separate port `telemetry.metrics.listen`); HTTP metrics — `reasonr_http_requests_total{route,code}`, `reasonr_http_request_seconds{route}`; a request log line — method, path, tenant, caller, code, time, position, incident.
6. **Composition**: `engine.yaml` (`engine/config`), a registry of factories by `type` (`engine/registry`), built-in adapters (`engine/builtin`: `memory`, `http`, `jwt`, `keys`), assembly and roles (`engine/stateless`): `api`, `timers` (once a second leases the fired timers and runs them through the kernel), `dispatch` (empty for now).
7. **`reasonrd`** is a separate module (`cmd/reasonrd`, `go.work`): it compiles the models of the data tenants from `--model`, assembles the engine by `--config` (without it — everything in memory, HTTP on `:8080`), `--roles`, `--test`, a graceful stop on SIGINT/SIGTERM. A configuration example — `cmd/reasonrd/engine.example.yaml`.
8. **Checks**: API tests on `httptest` (an end-to-end taxi scenario with notifications over WebSocket and long polling, every response code, JWT, idempotency, access to subscriptions, OpenAPI, metrics), authentication (signatures, expiry, audience, JWKS with RS256 and ES256), configuration (the plan's full example, errors with line numbers), engine assembly (projection placement, configuration errors, the `timers` role), an end-to-end `reasonrd` test (two data tenants with the models `base` and `acme`, API keys, test mode, stopping). `make check` checks both modules.

## E3

1. **`adapters/postgres`** is a separate module on `pgx` v5.7 (Go 1.23, like the kernel). It registers `postgres` as a store (`dsn` or `dsn_env`, `tenancy: column | rls`, `max_conns`) and as a hub (by default on the connections of the main store).
2. **Storage** (decision 7): a row per entity or projection row — `state jsonb` in the canonical JSON and the index key columns. The column types give SQL the same order as `reasonr.Compare`: strings — `collate "C"`, `timestamp` — `numeric` nanoseconds, an enum — the value number, `int`, `date`, `time`, `duration` — `bigint`, uuid — `uuid`. Composite values in keys are `bytea` (equality only; an ordered search over them runs in Go).
3. **Commit** is one transaction: the fired timer, entity versions, synchronous projections (a row is read `for update` once, the operations apply in order), the database's unique indexes (error 23505 by index name → `UniqueViolation` with the key from the record), timers, `forget` (erasing personal fields in every row of the tenant, as in memory), the outbox with `xid8`, the response by idempotency key; serialization and deadlock errors become `ErrConflict`.
4. **Search**: conditions, order (`asc nulls first` / `desc nulls last`) and the page are in SQL; keyset pagination by an expanded "after the cursor" condition, with the same cursor as memory. If a condition or a sort key is not on a key column, the rows of the type are filtered and sorted in Go by the shared functions of `engine/storekit`.
5. **An outbox without losses**: `bigserial` assigns the position before commit, so a transaction with a smaller position may commit later. Reading goes strictly by increasing position and stops at a gap, remembering a bound — the snapshot's `xmax`; the gap is skipped for good once the snapshot's `xmin` passes the bound (every transaction that could have taken the position has finished). Checked by a test with an uncommitted and a rolled-back transaction.
6. **Timers**: a lease with `for update skip locked`, the moment and the lease are Unix nanoseconds (`bigint`), the scheduling order is `seq`; retry and dead timers — as in memory; `reasonrd timers retry` puts dead ones back to work.
7. **The notification hub**: `pg_notify` into a channel of its own database schema, each instance has a listener and local subscribers; a notification over 7900 bytes is written to `rt_hub_payloads` and a reference goes into the channel; on a lost connection the listener reconnects.
8. **RLS** (`tenancy: rls`): policies on the entity and projection tables with `force row level security`, the tenant — `set_config('reasonr.tenant', …, true)` in every read and write transaction. Checked under a non-superuser role (RLS does not apply to a superuser).
9. **Schema and migrations** (§9.5): at start and in `reasonrd migrate` — a compatibility check against the last schema in `rt_schema_versions` (`compat.Check`, E11xx errors stop the server), then DDL: tables, key columns (new ones are filled from `state` for the rows of the model's tenants, fields with old names by `was`), indexes; before a unique index — a duplicate check with a list of repeats; all in one transaction under an advisory lock. Manual migrations — `reasonrd migrate --run <name> [--tenant t]`.
10. **The shared parts of stores** moved to `engine/storekit`: paths in a record, search conditions and order, cursors, a partial upsert, uniqueness keys, erasing personal data, encoding a value without a schema for the hub. Memory uses them too.
11. **Checks** (on PostgreSQL 17 in Docker, in CI — the `postgres:17` service): the conformance suites `RunUnitStore` (also with RLS), `RunProjectionStore`, `RunHub`; RLS isolation; migrations (a rename, a new field, indexes with filling, a unique index with duplicates); the outbox with out-of-order commits and a rollback; 20 concurrent commands on one entity; concurrent timer leases by two instances; **every scenario test of the examples (taxi, `acme`, bank) on the kernel with the PostgreSQL store** with the determinism check; an end-to-end `reasonrd` (taxi through the hub, a restart keeping the data, `migrate`, `timers retry`, refusing to start with an incompatible model). `-race` is clean.

## E5

1. **Test mode** (`reasonrd --test`, `engine/testapi`): `POST /_test/tenants` creates an ephemeral data tenant with a model (`base` or any extension of the module) and a virtual clock (2026-01-01); `POST /_test/{tenant}/clock` moves the clock, timers fire synchronously one by one, like `time passes` in memory, and the response is the errors of their commands; `GET /_test/{tenant}/captured` returns notifications to other actors (the hub records them) and external requests (from the outbox) after given numbers; `POST /_test/{tenant}/ids/{Type}` — a sequence number; `DELETE /_test/tenants/{tenant}` deletes the tenant's data. The `timers` role does not work in test mode.
2. **`reasonr test --engine http --url … [--parallel 8]`**: the driver `testrun.HTTPDriver` encodes the steps in the canonical JSON by the model's local schema; a command — `POST`, a query — `GET` with the `after` of the last command, notifications to the initiator — from the response (the recipient is the caller), to other actors and external requests — from `/captured`; the driver generates uuids, the server sequences. The report is the same as with `--engine memory`.
3. **Criterion §17, item 2 is met**: the taxi (base and `acme`) and bank tests pass through the HTTP API on both the memory adapters and PostgreSQL (`TestScenariosHTTP`, `TestScenariosHTTPPostgres`).
4. **The load test** — `cmd/reasonrd/server/load_test.go` (`REASONR_LOAD=30s REASONR_LOAD_CLIENTS=64`): each client loops over `SignUp`, `OrderTaxi`, `DriverFound`, `Accept`, `FinishRide` (commands) and `Card`, `FreeDrivers` (queries). The setup: Apple M1 Max without low power mode, one `reasonrd` process inside the test process, PostgreSQL 17 in Docker Desktop (10 CPUs), runs of 20 s, no failures:

   | Clients | Commands/s | Commands p50 / p99 | Queries/s | Queries p50 / p99 |
   |---|---|---|---|---|
   | 16 | 1897 | 8.1 / 12.9 ms | 759 | 1.2 / 2.4 ms |
   | 64 | 2425 | 25 / 41 ms | 970 | 3.7 / 7.2 ms |
   | 128 | 2408 | 49 / 77 ms | 963 | 13 / 25 ms |

   The ceiling is about 2400 commands a second, reached by 64 clients; beyond that only the latency grows. The goal of §11.3 (3000 commands a second at p99 < 30 ms on 8 vCPUs and two instances) is not met on this setup; at 16 clients the command p99 is 13 ms. In macOS low power mode the same test gave 2005 commands a second at 64 clients.
5. **Profile**: 70% of the server's CPU is the system calls of the network exchange with PostgreSQL; a commit is about ten sequential round trips (begin, tenant and xid, entity versions, reading and writing projections, outbox, commit), and the Docker Desktop network on macOS makes them more expensive. Already fixed: the outbox NOTIFY moved out of the commit transaction and is debounced (at most once every 5 ms) — it serialized commits and cost a third of the throughput (1240 → 1934 commands a second, measured in low power mode); the tenant and the xid in one query (→ 2005). Next step — batching the commit queries (pgx Batch: two round trips instead of ten) and measuring on Linux without Docker Desktop with two instances.

## E6: MongoDB

1. **`adapters/mongodb`** is a separate module on `go.mongodb.org/mongo-driver/v2` v2.3 (Go 1.23). It implements `UnitStore`, `ProjectionStore`, `TimerSource`, `EffectSource`, `Coordinator`, `EventSink`, `SchemaStore` and deleting a tenant; the type `mongodb` in `engine.yaml` (`uri` or `uri_env`, `database`); part of the standard `reasonrd`. It needs a replica set: a unit of work is committed in a transaction.
2. **A record document**: `_id {t: tenant, id}`, `tenant`, `id`, `version`, `state` — the canonical JSON as a string, `k_…` — the index keys in types ordered like `reasonr.Compare` (int64, Decimal128 for `decimal` and `timestamp` nanoseconds, strings, binary uuids); none — the field is absent (sorts first, does not take part in a partial unique index). `bytes` and composite keys are binary; an ordered search over them runs in Go.
3. **Commit** — `WithTransaction`: the fired timer, versions (`replace` with a condition on the version), synchronous projections, uniqueness (a duplicate in the `u_…` index → `UniqueViolation`, a duplicate `_id` → a conflict), timers, `forget`, the outbox, the idempotency key. Write conflicts the driver did not resolve by retrying become `ErrConflict`.
4. **Outbox positions without a hot document in transactions**: an atomic counter update before the transaction assigns the position, with an "in progress" mark; after the transaction the mark is removed. A reader at a gap waits while the position is in progress; if it is neither in progress nor in the outbox, the transaction rolled back and the gap is final. A mark older than 70 s counts as a rollback: MongoDB aborts transactions longer than 60 s. Timer order numbers are also assigned before the transaction. The first version incremented the counters inside the transaction: under load every commit conflicted on one document — 82 commands a second at p99 9.7 s; now 1301 at p99 82 ms.
5. **Timers** are leased one by one with an atomic `findOneAndUpdate` (MongoDB has no `skip locked`); the schema — indexes (unique ones are partial on the fields being present), a duplicate check before a unique index, recomputing the key fields when the schema changes, versions in `rt_schema_versions`.
6. **The shared format of outbox records and of responses by key** moved from the PostgreSQL adapter to `engine/storekit` (`payload.go`).
7. **Checks** on MongoDB 7 in Docker (`make mongo-up`, `REASONR_TEST_MONGODB`; the same container in CI): the conformance suites `RunUnitStore`, `RunProjectionStore`, `RunCoordinator`; the scenario tests of the examples on the kernel with the MongoDB store with the determinism check and through the HTTP API (`reasonrd --test`); migrations (`was`, a new field, indexes with recomputed keys, a unique index with duplicates); 20 concurrent commands on one entity.
8. **Load** (`REASONR_LOAD_STORE=mongodb`, the same setup as for PostgreSQL, 15 s, no failures): 16 clients — 754 commands a second, p50 20 ms, p99 38 ms, queries p99 2.8 ms; 64 clients — 1301 commands a second, p50 47 ms, p99 82 ms, 520 queries a second, p99 5.9 ms. That is about half the throughput of PostgreSQL on the same setup: every commit has two counter round trips outside the transaction and removing the mark after it, and MongoDB transactions are more expensive.

## Deviations from the plan and decisions it did not cover

1. **A position is one sequence per main store**, not per tenant: `EffectSource.Read` reads the stream of every tenant, like the `bigserial` in `rt_outbox` or a journal index. Within a tenant positions grow too, so `after` and `Applied` work as described in §3.4.
2. **A unit of work without model effects gets no position**: a rejected command with a key (only the response is stored) and deleting a timer after a business error return position 0 and do not get into the outbox.
3. **The idempotency key stores the response of a rejected command too** (the errors), not only of an accepted one: a retry gets the same errors even if the state has changed since.
4. **`Unit` separates projection operations**: `Projections` (synchronous, applied in the transaction) and `Async` (only into the outbox). `CommittedUnit.Projections` holds only the asynchronous ones. There are no notifications in the outbox: they are not stored (RFC §13).
5. **Schemas come from the catalog, not with every call**: adapters get a `port.Catalog` (tenant → schema) on creation, and the methods take only the tenant, as in the sketches of §4.
6. **`TimerSource`**: the sketch's `Release` is split into `Retry(t, at)` and `Dead(t, reason)`; `LeaseRequest.Tenant` allows selecting the timers of one tenant (the virtual clocks of the E5 test mode), `""` — of all. The retry pause is 1, 2, 4… s, **but no more than 10 minutes** (the plan does not say).
7. **The determinism check in the kernel replays identifiers**: the second run gets the same uuids and sequences from the journal of the first, and an extra or different request is `ErrNondetermined`. The in-memory engine used to roll back its counters; the kernel does not know how a store's counters work.
8. **The delivery journal of the in-memory engine** is ordered: notifications to the initiator, then to other actors, then the external requests of each unit of work. In a unit of work where notifications to the initiator and to others alternate, the order in `reasonr test -v` may differ from before; the `then` checks do not depend on order, the expected files did not change.
9. **The in-memory hub** keeps up to 64 unread notifications per subscription; if the buffer is full, the notification is lost (delivery is at most once).
10. **The JSON of a duration** is the largest unit in which the duration is whole, like `string(x)` in the language: `"90m"`, not the `"1h30m"` of the plan's table in §8.2; a compound form is accepted on input. Durations that are not a multiple of a millisecond use `ns`. The table in the plan and RFC §31.3 are fixed.
11. **JSON on input**: an unknown field is an error (for the state of an earlier model version — `IgnoreUnknown`); a field is accepted under its old name too (`was`); a `map` with an optional key is written as an array of pairs; a `PageRequest` without `size` is an error; a `float` infinity and `NaN`, a string that is not UTF-8 are encoding errors.
12. **Kernel metric names**: `reasonr_commands_total{outcome}`, `reasonr_command_seconds`, `reasonr_conflicts_total`, `reasonr_timers_total{outcome}`.

### E2

13. **The package `edge/httpapi`**, not `edge/http`: the name `http` would clash with `net/http` in every transport file.
14. **Our own YAML parser**, the subset `engine.yaml` needs: block and one-line flow mappings and lists, quoted strings, comments. The kernel stays without dependencies (decision 6). An unknown key in the configuration is an error with a line number, not a silently ignored setting.
15. **Secrets need not be written in `engine.yaml`**: `secret_env`, `key_env` are names of environment variables.
16. **A query response is the result value itself** (an object, a `page`), without a `{"status": …}` wrapper: only command responses and errors have the wrapper.
17. **A token in the `access_token` parameter** is accepted by `/api/ws` and `/api/poll`: a browser does not set the `Authorization` header on a WebSocket.
18. **Response codes not in the plan's table**: an unknown tenant, or one not set up in the model — 401; a `GET` on a command path — 405 (as the `net/http` router answers); a subscription by a non-actor — 403; a replay by key is marked with the header `Idempotent-Replayed: true`. `invalidArgument` rules the VM does not have: `unknown` (an extra field or parameter), `count` (a query parameter repeats).
19. **The long polling format**: `{"cursor": "N", "notifications": [ … ]}`; the cursor is the number of the last notification returned, the default wait is 30 s, at most 60 s.
20. **`/openapi.json` without credentials** returns the model of the tenant `default`.
21. **Not done in E2**: request bodies in the log (by a flag, without personal fields), tracing (`Tracer` is only `Nop`), the notification hub between instances (PostgreSQL LISTEN/NOTIFY — E3). `reasonr engine check` and `reasonr engine build` did not explicitly make it into the stage plan; engine assembly already rejects at start an asynchronous projection with a unique index, unknown `type`s and projections. The check "commands check the existence of projection rows" and both CLI commands were proposed for E4, with the dispatcher, once asynchronous projections work. While there is no dispatcher, `reasonrd` warns in the log that asynchronous projections are not filled.

### E3

22. **`reasonrd migrate` and `reasonrd timers retry`** instead of `reasonr migrate` and `reasonr timers retry`: the `reasonr` CLI is the kernel without dependencies, and the PostgreSQL driver is only in the server module.
23. **The pause before a retry on a version conflict** is random, with an upper bound of 1, 2, 4… ms, at most 50 ms: without it 20 concurrent commands on one entity used up 16 attempts (the "hot entities" risk, §16 of the plan).
24. **`port.UnitStore.Remembered` gets the time** by the engine clock: the idempotency key expiry is compared with it, not with the database clock (tests have virtual clocks). Added the port `port.SchemaStore` (`LastSchema`, `EnsureSchema`) — for stores that need the schema in advance.
25. **Column types not in RFC §31.2**: `timestamp` in keys is `numeric` nanoseconds, not `timestamptz` (PostgreSQL microseconds would give a different order and equality than the model); a timer's moment and lease are `bigint` nanoseconds. The SQL example in RFC §31.2 is fixed.
26. **Service tables beyond the plan**: `rt_sequences` (sequence identifiers), `rt_forgotten` (forgotten subjects), `rt_applied` (the position of asynchronous projections), `rt_hub_payloads` (large notifications). The tables `rt_cursors` and `rt_leases` come with the dispatcher (E4).
27. **A uniqueness violation is checked on every write**, not by the final state of the unit of work as in memory: if one command swaps the unique values of two records, PostgreSQL reports a violation. The example models have no such case.
28. **The event journal of an entity** is not kept in the main PostgreSQL store: events go into the outbox, and the journal is the `EventSink` port (E4).
29. **Reading the schema for DDL**: key columns and indexes are the union over every model that uses the table (the base and extensions); for rows of a tenant of another model the key columns of its extension are empty.
30. **The example `engine.postgres.yaml`** and the targets `make pg-up` / `make pg-down` (PostgreSQL 17 in Docker on port 55432).

## E4

1. **The dispatcher** (`engine/dispatch`): each consumer has a lease `dispatch:<name>` (one instance handles the stream, the order is kept), a cursor in the main store, reads the outbox in batches, waits for new records (`EffectSource.Wait`), retries after a failure with a pause, keeps dead letters; `reasonrd dispatch retry [--consumer]` delivers them again.
2. **Consumers**: `projections:<store>` — asynchronous projections, `events` — the event journal (`ev_events` in PostgreSQL, `memory.Store` in memory), `requests` — the integration service (`edge/integration`: `POST {url}/requests/{System}/{request}`, `Idempotency-Key`, 4xx — a refusal, 5xx and network errors — retries), `bus` — the bus (`log`; Kafka is RFC stage 5).
3. **`reasonr engine check`** (`engine/check`, and at the start of `reasonrd`): an asynchronous projection with a unique index (C0001) or with a row existence check in commands — by the bytecode, the operations `rec.load` and `ref.exists` in commands, event application, rules, methods and reactions (C0002); unknown projections (C0003) and external systems (C0005) in the configuration; an external system without a transport (C0004, a warning); an unknown event in `bus.publish` (C0006). The output is text or JSON of the same shape as `reasonr check`.
4. **`reasonr engine build`**: the manifest `components.yaml` (the module, the adapter packages, local module replacements) → `main.go` and `go.mod` in a temporary directory → `go mod tidy` and `go build`. The server moved into the package `cmd/reasonrd/server` for this; the standard `reasonrd` is the same `main` with the memory and PostgreSQL adapters. A test builds the server with a third-party adapter (`cmd/reasonr/testdata/fakeadapter`) and runs it.
5. **Checks**: the conformance suite `RunCoordinator` on memory and PostgreSQL; the event journal is idempotent by position; the dispatcher — an asynchronous projection and `after`, a restart without losses or double delivery, external requests with retries and the same key, a dead letter and its retry, the bus; **an end-to-end scenario on PostgreSQL**: taxi with an asynchronous `OrderMart` in a second store, the event journal there too, a recording integration service and `dispatch retry`.

### E4

31. **The port `port.Coordinator`** (consumer cursors, leases, dead letters) lives in the main store; the in-memory store has a single-process `memory.Coordinator`.
32. **Dispatcher consumers**: `projections:<store>` (every unit of work marks its position so that `Applied` keeps up with the stream), `events`, `requests`, `bus`. The retry pause is 1, 2, 4… s, at most a minute; an external request without a `timeout` in the model is retried for an hour (`DefaultRequestTimeout`), then it becomes a dead letter.
33. **The schema is brought up to date in every store** that needs it (the main one, the projections', the event journal's).
34. **The `log` bus** writes events to the log for debugging; Kafka is RFC stage 5.
35. **The codes of `reasonr engine check` are `C0001`…`C0006`**, separate from the codes of model diagnostics (`E`, `W`): they have no `reasonr diag explain` explanations and are about the configuration, not the model.
36. **The `reasonrd` server refuses to start** on `engine check` errors; it logs warnings.
37. **An external request without a transport** becomes a dead letter with a reason; and if there is no `requests` consumer at all (no `integrations`), requests wait in the outbox and `engine check` warns (C0004). When a transport appears, the consumer starts from the beginning of the outbox and delivers every accumulated request.

### E5

38. **`reasonr test --engine http` requires `--url`**: the CLI is a kernel module without drivers and cannot start `reasonrd` itself; RFC §27.3 is fixed.
39. **Errors and notifications in API responses have a `type` field** — the type that declared them: the name of an error or a notification is not unique across types, and tests and clients need to know the owner.
40. **Outbox records of a deleted tenant** are returned without effects: the position moves on, there is nothing to deliver.
41. **The outbox NOTIFY is outside the commit transaction** and at most once every 5 ms: an outbox reader learns about a new record with a delay of up to 5 ms (plus a check once a second).

### E6

42. **The state in MongoDB is a string of the canonical JSON**, not a nested BSON document: the same format as in PostgreSQL and the outbox, no conversion between JSON and BSON; the key fields serve search.
43. **Outbox positions in MongoDB have gaps** (the positions of rolled-back transactions): increasing, without losses, but not consecutive.
44. **There is no notification hub on MongoDB** (the plan did not require one): with a MongoDB main store the hub is `memory` (one process) or `postgres`.
