# Plan: performance tests at 10 million lines of code

| | |
|---|---|
| **Basis** | [Roadmap](https://github.com/tycheg/reasonr-compiler/blob/main/docs/roadmap.md), item 7 |
| **Status** | S1, S2 — done; S4 — partly; S3 — not done, a proposal in §5 (2026-11-13) |
| **Branch** | `scale-10m` |

The plan is carried into two repositories: the compiler (open stage S3) and the engine (open stage S4).

---

## 1. Goal

Check and ensure that the tools and the engine work on a model the size of a large enterprise system — **10 million lines of `*.rr`** (about 2,000 bounded contexts, 20,000 entities, 200,000 commands, 100,000 tests): the compiler, the LSP, tests, the engine. So far everything is checked on examples of hundreds of lines; the asymptotics were never measured.

## 2. Decisions (proposal)

| # | Decision |
|---|---|
| 1 | **A synthetic model generator** `go run ./internal/genmodel --lines 10m --seed 1` (in `compiler/`): systems, bounded contexts, entities with links, commands with events, calls and reactions, queries with indexes, projections, screens and apps, tests, extensions, fakes; size distributions follow real projects (an average entity ~ 300 lines, 20 % of bounded contexts with a UI). The model has no errors and is deterministic by seed; sizes — 100k, 1m, 10m |
| 2 | **Budgets (proposal, §4):** on a developer machine (8 cores, 32 GB) for 10 million lines — `reasonr check` from scratch ≤ 60 s and ≤ 16 GB; a repeated `reasonr check` after editing one file ≤ 3 s; LSP: diagnostics after an edit ≤ 500 ms, go-to/hover ≤ 50 ms, opening the project ≤ 60 s; `reasonr build` ≤ 90 s; the engine start (loading the program) ≤ 10 s, program memory ≤ 4 GB; `reasonrd test` of 100,000 tests on memory ≤ 10 min on 8 cores |
| 3 | **Measurements in CI on a schedule** (`make scale`): time and peak memory by phase (parsing, names, types, checks, IR, bytecode, schema), a JSON report and a comparison with the previous run; a regression above 20 % is a failure |
| 4 | **Expected work** (by the measurement results): parallel parsing and checking of bodies by file and bounded context; **incremental compilation** — a cache of parsing and checking results by the hash of a file and of a bounded context's interface (what other bounded contexts see: public methods, types, events), rebuilding only dependent bounded contexts; the LSP on the incremental core instead of a full recheck of the model; lazy symbol indexes; streaming bytecode generation; the engine loading the program without a full copy of the schema per tenant |
| 5 | **pprof profiles** (CPU and memory) are attached to the `make scale` report for each phase |

## 3. Questions to the author

| Question | Proposal |
|---|---|
| Do the budgets of §2 fit? Especially "editing one file — 3 s" and LSP 500 ms | They are a Go/TypeScript-level target for such sizes |
| 10 million lines — one model (one module) or a project of many modules? | One project of modules; dependency modules are checked through the cache and not rechecked (decision 4) |
| The machine for CI measurements | A dedicated runner with fixed hardware, otherwise the comparison is noisy |

## 4. Stages

| Stage | Result |
|---|---|
| **S1. Generator and measurements** | A model generator for 100k/1m/10m, `make scale`, a report by phase and profiles; the first numbers go into the plan |
| **S2. Compiler** | Parallel phases, removing the quadratic spots found in S1; the "from scratch" budget |
| **S3. Incrementality** | A cache by file and bounded context interface; `reasonr check` after an edit; the LSP on the cache |
| **S4. Engine and tests** | Loading the program, memory, `reasonrd test` on 100,000 tests (together with item 10 — workers) |

Done when every budget of §2 is met on the 10-million-line model in `make scale`, and the measurements run on a schedule.

## 5. Progress

| Stage | Status | What is done |
|---|---|---|
| S1. Generator and measurements | Done | `compiler/internal/genmodel` (the command is `internal/genmodel/cmd/genmodel`): bounded contexts of 4–12 aggregates with commands, events, calls between aggregates, index queries, an ACL to a neighboring bounded context, tests; 20 % of bounded contexts have screens and an app; the model has no diagnostics (a test) and is deterministic by seed. `make scale [SCALE=100k\|1m\|10m]`: `compiler/internal/scale` — time, allocated memory and the live heap by phase, pprof profiles (CPU and heap) per phase, budgets, a comparison with the previous report (+20 % and ≥ 100 ms is a failure); `engine/internal/scale` — the build, loading the program into the interpreter, running the tests on memory. `REASONR_CPUPROFILE=file reasonr …` profiles any command |
| S2. Compiler | Done | Quadratic spots: finding an aggregate by position, a method by name in tests, a declaration by short name, a bounded context and a file by position (sema, check, lower) — indexes and bisection; an IR function by name (`ir.Program.Func`, `ir.Verify`) — an index; ACL reactions in the schema — one pass; the method owner in lower — an index. Reading and parsing files run in parallel, FileSet places follow the file order (positions are deterministic). Tokens without reallocations. `reasonr build` built both the test and the working model — now only the working one |
| S3. Incrementality | **Not done** | A repeated check after editing one file at 10 million lines takes 19.9 s (budget 3 s): parsing comes from the cache, but names, types and analyzers check the whole model. A cache of check results by bounded context and bounded context interface is needed (decision 4) — a rework of sema; the LSP on it too. Taken out as a separate stage, see below |
| S4. Engine and tests | Partly | `reasonrd test` on memory runs tests in parallel (`--parallel`, the number of cores by default; each test on its own engine). Loading a built program into the interpreter is within budget; the engine cannot yet load an already built program without compiling (a `reasonr build` artifact): starting `reasonrd --model` at 10 million lines includes compilation |

**Measurements** (a MacBook, 10 cores, 32 GB; the model `--seed 1`):

| | 100k | 1m | 10m | 10m budget |
|---|---|---|---|---|
| Lines / files | 101,790 / 681 | 1,000,391 / 6,948 | 10,000,077 / 69,433 | |
| Aggregates / commands / tests | 457 / 4,057 / 1,882 | 4,478 / 39,734 / 18,478 | 44,765 / 397,256 / 184,687 | |
| `reasonr check` (CLI), before → after | 0.35 s | 21.2 → 2.0 s | 31.7 → 20.5 s ¹ | ≤ 60 s ✓ |
| Peak memory of `reasonr check` | 0.1 GB | 0.9 GB | 8.5 GB | ≤ 16 GB ✓ |
| `reasonr build` (CLI), before → after | | 11.7 → 4.8 s | 194 → 44 s | ≤ 90 s ✓ |
| Repeated check (parse cache) | 0.13 s | 1.3 s | 19.9 s | ≤ 3 s ✗ |
| Loading the program into the interpreter | 17 ms | 0.35 s, 218 MB | ≈ 3.5 s, ≈ 2.2 GB ² | ≤ 10 s, ≤ 4 GB ✓ |
| Tests on memory, 10 threads | 1,882 in 0.04 s | 18,478 in 3.2 s | ≈ 185,000 in ≈ 35 s ² | 100,000 ≤ 10 min ✓ |

¹ 31.7 s is already after the sema indexes; before them 1m took 21 s, and 10m did not finish in reasonable time. ² An estimate from 1m: the growth is linear; a direct 10m engine measurement was not made (together with the build — about 13 GB of heap).

**10m phases** (`make scale SCALE=10m`): parsing 2.6 s, names and types 12.0 s, analyzers 5.9 s, IR 13.3 s, IR verification 1.6 s, schema 1.7 s, bytecode 6.6 s, interface 0.05 s. The longest are the single-threaded sema and analyzers; garbage collection runs on idle cores (GOGC 200–400 barely changes the time).

**Deviations from the plan.**
- The generator is the package `internal/genmodel` and the command `internal/genmodel/cmd/genmodel` (not `go run ./internal/genmodel`): the measurement tool needs the same generator. The generator does not build extensions and fakes yet.
- The budgets in `make scale` scale linearly with the model size (1m gets a tenth of the 10m budget); memory is the live heap after check (800 MB per million lines), not the process peak: the measuring process holds both the test and the working model.
- The measurements are local; the CI schedule is not set up (no dedicated runner, the question in §3).
- The LSP was not measured separately: it runs on the same full recomputation as a repeated check — the LSP budgets wait for S3.

**S3 — a proposal for the author's decision.** A check cache by bounded context: for each bounded context, the hash of its files and the hash of its interface (public commands and queries, events, types and identifiers — what other bounded contexts, tests and apps see). An edit that does not change the interface rechecks only the bodies of its own bounded context; an interface change also rechecks the bounded contexts, tests and apps that see it. For that sema must be able to check the bodies of some files against the declarations of the whole model and keep the results by file (expression types, calls, diagnostics) so that they can be taken from the cache; the analyzers likewise by bounded context, except the cross-context ones (PII, the call graph), which are recomputed from stored summaries. The estimate is a separate plan the size of a stage.
