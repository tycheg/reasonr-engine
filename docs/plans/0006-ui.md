## 1. Goal and scope

**Goal:** a product engineer builds the interface in ReasonR without TypeScript (RFC §22):

- describes apps and screens made of primitives, and gets an automatic UI where a layout is not needed;
- the compiler checks the layout: bindings, implicit arguments, access, texts;
- the app works in a browser on the standard catalog of primitives; UI developers add their own primitives;
- the model's scenario tests pass through the browser in every place of the UI.

**What already exists:**

| Part | Where | State |
|---|---|---|
| The old syntax: `view`, `action`, `control`, `item`, `via` | `compiler/ast/view.go`, `parser/decl.go`, `parser/test.go`, `sema/views.go`, `sema/tests.go`, `format`, `lsp`, `tools/explain.go`, `schemagen`, `compat`; E0701–E0705, E0805, W1011 | Replaced (decision 1) |
| The schema: `TypeView`, `TypeControl`, `ViewInfo`, `ViewItem` | `schema.go` | Removed; the interface is a separate program (decision 2) |
| The model's HTTP API, notifications over WebSocket and long polling, `/openapi.json` | `edge/httpapi` | Done; WebSocket authenticates only with a header — a browser does not set it (§5.4) |
| Test mode: ephemeral tenants, clocks, fakes, `Authorization: Test …` | `engine/testapi`, `reasonrd --test` | Done; signing in to the UI is added (§5.5) |
| The scenario test runner: the drivers `memory`, `http` | `testrun`, `runtime/vm` (`Driver`) | Done; a `web` driver is added |
| The expression interpreter | `compiler/lower`, `runtime/vm` | Done; used for `if` and for computing bindings on the server (decision 4) |
| The taxi UI in the old syntax | `examples/taxi/ui.rr` | Rewritten by RFC §22.3, §25.5 |

**In the plan:**

- the language: `app`, `screen`, `primitive`, `default`, `texts`; binding, access, places, texts; diagnostics, `fmt`, LSP, `explain`;
- the standard catalog `std/ui` (RFC §22.8): declarations in the compiler, implementations in React;
- the automatic UI: omitted parts and `app … auto`, `reasonr ui eject`;
- the UI program: screen descriptions by platform and language, `reasonr build --ui-types`;
- the server: the app API `/app/…`, loading screen data, place operations, the app's OpenAPI, serving the runtime;
- the web runtime; a module's own primitive implementations; signing in by OIDC and in `--test`;
- the runner `reasonr test --engine web`: `given` through the API, places and k runs, `--coverage`, `--place`, `--navigate path`;
- taxi: the passenger, driver and dispatcher apps and the admin with the model's additions (RFC §22.3), texts.

**Not in the plan:**

- mobile — stage 8: a screen description does not depend on the platform (§4), the runtime and the catalog for mobile are done there;
- the UI of tenant extensions (`extend screen … in Part`) — stage 7, with the rest of `extend`;
- a second language of the taxi texts: the `texts` mechanism and its checks are in, translating the example is not;
- offline mode, PWA, server-side rendering, a visual layout editor.

## 2. Decisions to approve

| # | Question | Proposed decision | Alternative |
|---|---|---|---|
| 1 | The old syntax | **Removed without a transition period:** there are no models outside the repository. `view`, `action`, `control`, `via` stop being keywords; the E07xx codes get new meanings (§3.5), E0805 and W1011 are removed | Supporting both syntaxes — two sets of rules and diagnostics for models that do not exist |
| 2 | Where the interface lives in the compiled model | **A separate UI program** `reasonr.UI` next to the schema: apps, screens, primitives, texts. The model's schema (`reasonr.Schema`) holds no interface: storage, compatibility (`compat`) and migrations do not touch it | The types `TypeApp`, `TypeScreen`, `TypePrimitive` in the schema (as RFC §29 says now) — `compat` and the engine see what they do not need; RFC §29 is refined (§16) |
| 3 | The standard catalog | **A file `std/ui.rr` inside the compiler** (`go:embed`), included in every module implicitly, like the built-in types. The catalog's names cannot be redeclared. A module adds its own primitives with ordinary declarations | The catalog as a separate module included explicitly — an extra step in every model |
| 4 | Where `if` and screen data are computed | **On the server.** `if` conditions and binding expressions compile to bytecode (like rules) and the interpreter runs them when screen data is loaded. There is no interpreter in the browser: the client gets the data, the computed `if`s and the list of available nodes | Computing `if` in the browser — a second interpreter in TypeScript, which must match the Go one |
| 5 | Screen data | **One request per screen:** the server runs the screen's queries along the tree (nested ones after those whose data they depend on), in one read snapshot, and returns the data, the `if`s and availability. Tables and lists return the first page; the next ones — by a place request | A request per node from the browser — N requests per screen, and an `if` over the data of neighboring nodes cannot be computed |
| 6 | Place operations | **A whitelist:** `POST /app/{App}/{Screen}/{place}` calls only this place's method; the arguments come from the client whole, the command checks access and rules (RFC §22.4). The server checks that the place exists in the app and that the method is available to the caller | The server recomputes fixed arguments from the screen parameters — double work with no security gain: the screen parameters come from the client too |
| 7 | The web runtime and the catalog implementations | **TypeScript + React + Vite** in the `web/` directory (npm workspaces): `@reasonr/runtime` (binding, data, forms, navigation, notifications, labels) and `@reasonr/std-ui` (the catalog implementations on **Ant Design**). The runtime does not depend on the component library; the library lives inside the primitive implementations | Implementations without a library, on our own components — longer and worse for accessibility; another library — swapped later one primitive at a time (RFC §31.4) |
| 8 | The default build in `reasonrd` | **A built-in build** (the runtime + the standard catalog) lives in the repository (`edge/webui/dist`), `go:embed`; `make web` updates it, CI checks that it matches the sources. A model without its own primitives needs no Node, and `go install` gives a `reasonrd` with a UI | Building at release — `go install` from sources would give a `reasonrd` without a UI |
| 9 | Own primitive implementations | **The module's `ui/web/` directory**, a file per primitive (`EntityPicker.tsx`); the UI developer builds it (`npm run build`, the plugin `@reasonr/vite`), the result is `ingress.ui.dir`. The plugin checks the implementations against the declarations (interfaces from `reasonr build --ui-types`). A primitive without an implementation is drawn by the automatic UI (RFC §22.1) | Building from `reasonr` by calling npm — a Go tool depending on Node |
| 10 | Signing in | **In `--test`** — a "sign in as" panel: an actor and an id or a role, a tenant; requests with `Authorization: Test …`. **In production mode** — OIDC, the authorization code flow + PKCE (`ingress.ui.auth.oidc`); the existing `auth: jwt` verifies the IdP token | Only test sign-in in this stage — the app could not be shown at the pilot (stage 9) |
| 11 | WebSocket from a browser | **The token in a subprotocol** `Sec-WebSocket-Protocol: reasonr, bearer.<token>`; long polling — with the ordinary header | The token in the URL — it ends up in proxy logs |
| 12 | The browser runner | **`playwright-go` in a separate module `testrun/web`** (like `adapters/kafka`): the dependency does not get into the kernel; `reasonr test --engine web --install` installs the browsers; Chromium by default | `chromedp` — Chrome only, no auto-waiting; a runner on Node — a second runner with its own report |
| 13 | The language of texts in a response | **A screen description is built in the user's language** (`Accept-Language` or a choice in the UI; RFC §22.11): the client gets only the texts it needs. The description hash includes the language | Every language in every description — the size grows with the number of languages |
| 14 | Interface diagnostic codes | **The E07xx range anew** (RFC §28.3, "Interface"), warnings — W13xx | A new range E13xx with E07xx empty — a hole in the numbering for no benefit |

## 3. The compiler

### 3.1. Syntax

- The lexer and the parser: `app`, `screen`, `primitive`, `texts`, `default` at the top level; layout lines (RFC §22.3) — a primitive, a field, a part, `on`; string labels; `if`; type variables and variant types (`|`) only in primitive declarations; a query parameter `search(text string) list<R>`, `field<R, K>`, `= auto`; `texts` keys (`Screen:binding#n`).
- The AST: `compiler/ast/ui.go` (an app, a screen, nodes), `compiler/ast/primitive.go` (a primitive declaration), `compiler/ast/texts.go`; `view.go` is removed.
- `via` in tests is removed (`parser/test.go`, `ast/test.go`), and E0805.
- `fmt`: the canonical form of layouts and primitive declarations; golden tests.

### 3.2. Primitives

`sema/primitive.go` checks declarations: type variables and constraints, `binds` (a bare type is a query result, `field`, `input`, `command`, `screen`), parameters and their default values, parts and their `binds`, events. For every binding of a primitive in a layout — **unification**: type variables are filled from the place (a query result, the type of a field or an input, the result of a query parameter), and `= auto` resolves to the only fitting field.

### 3.3. Layout

`sema/ui*.go` (a file per topic — apps, scopes, arguments, access, places):

1. **Scopes** (RFC §22.4): screen parameters and `me` → the primitive's data → a row → a form; a name is looked up from the nearest scope.
2. **Arguments** of queries and commands: explicit → same-named values of the scopes (the type matches) → an input; the command's **target** by type; fixed and editable values; an ambiguity is an error with the fix "bind explicitly".
3. **Parts:** lowercase names by the part's `binds`; omitted parts that bind data are marked for automatic filling (§4.1).
4. **Events and navigation:** screen parameters from the event's data, then from the scopes.
5. **Access:** the app (`app(…)`), nodes by the access of their methods (RFC §22.6); a node available to nobody who enters the app — a warning; a screen that cannot be reached — a warning.
6. **`default`:** the default primitive for a type — at the catalog, module or app level; an identifier input without `default` is an error.
7. **Places:** the list of the app's places (`Admin.AdminOrder:Order.Edit`, `#2`) — for descriptions, labels and the runner.
8. **`if`** — an expression over the scopes, of type `bool`; compiled to bytecode (decision 4).
9. **The apps of a screen:** a screen belongs to every app from which it can be reached; `me` and access are checked for each.

### 3.4. Texts

`sema/texts.go`: `texts` keys refer to existing names and nodes; substitutions `{…}` are parameters of an error or a notification; layout strings are texts of the app's base language (`language`); a warning about base-language texts missing from another language of the model.

### 3.5. Diagnostics

The E07xx range anew (decision 14), warnings — W13xx. Each with an explanation for `reasonr diag explain`, an example of the error and the fix; where possible — with `fixes` for agents (`AGENTS.md`).

| Group | What is checked |
|---|---|
| Declarations | A repeated name of an app, a screen, a primitive; the catalog's names are not redeclared; a type variable, a constraint, a binding kind, a part type, a query parameter, `= auto` without a fitting option |
| Bindings | The method is not public; the binding kind does not match the primitive's declaration (a query with a page for `Card`); a field of the wrong type; a screen without all its parameters |
| Parts | A name not found in the part (`driverPhone` in `Columns`); a row in a part without `binds`; an unknown part |
| Arguments and target | An ambiguity; the type of a same-named value does not match; an identifier input without `default`; an argument of a query parameter not bound to the value passed (`text`) |
| Navigation | An unknown event; the screen parameters are not filled |
| Access | A node available to nobody in the app (W); an unreachable screen (W); `me` without an actor type in the app |
| Texts | A key not found; a substitution that is not a parameter; a missing translation (W) |

### 3.6. Tools

- The LSP: highlighting, go to the definition of a primitive and a method, completion of part, field and parameter names by `binds`, a hint "where the argument comes from" on a layout line, diagnostics.
- `reasonr explain Admin` — an app: screens, places, commands that have nowhere to go (RFC §22.9); `reasonr explain Admin.AdminOrder` — a screen: nodes, places and argument sources.
- `reasonr graph` — navigation between an app's screens.
- `reasonr ui eject <app>` — the layout `auto` builds, through `fmt`.

## 4. The UI program and screen descriptions

### 4.1. The automatic UI

`compiler/ui/auto.go` builds the missing layout by the rules of RFC §22.9 **before** the semantic checks of the layout: omitted parts that bind data and `auto` apps turn into ordinary nodes and then take the common path. So `eject` prints exactly what runs.

### 4.2. The UI program

`reasonr.UI` (decision 2) is a compilation result next to the schema and the bytecode:

| Part | What is in it |
|---|---|
| Apps | Access, `platforms`, the menu, screens, places |
| Screens | Parameters, a tree of nodes with primitives, bindings (the method, the sources of arguments and the target), parts, `if` (a bytecode function number), navigation |
| Primitives | Declarations with the inferred types for each use |
| Texts | The app's base language, `texts` by language |

The UI program is built both for the test program and for the production one; fakes (RFC §18.1) do not get into it.

### 4.3. A screen description

A description is what a platform runtime gets (RFC §31.4): a JSON per screen, language and platform, without the model.

```json
{
  "screen": "AdminOrder",
  "params": [{ "name": "orderId", "type": "id" }],
  "title": "Order",
  "nodes": [
    { "id": 1, "primitive": "Card", "place": "Admin.AdminOrder:Order.Details",
      "fields": [{ "name": "status", "primitive": "Tag", "label": "Status" }, "…"],
      "parts": { "Actions": [
        { "id": 2, "primitive": "Edit", "place": "Admin.AdminOrder:Order.Edit", "label": "Edit", "if": true,
          "target": { "from": "data", "node": 1, "field": "orderId" },
          "inputs": [{ "name": "orderRoute", "primitive": "Group", "initial": { "node": 1, "field": "orderRoute" } }, "…"] }
      ] } }
  ],
  "types": { "OrderStatus": { "enum": ["searching", "…"], "labels": { "searching": "Looking for a driver" } } }
}
```

- Only the types the screen uses; labels in the response's language.
- The address carries a content hash (`AdminOrder.3f9a….json`) and is cached forever; a new model version changes the hashes of only the changed screens.
- The format is versioned (`version`) and checked by the runtime conformance suite (§11): it is the contract for mobile in stage 8.

### 4.4. Types for implementations

`reasonr build --ui-types [--platform web]` generates the interfaces of primitive implementations (RFC §22.7): `EntityPickerProps<R, K>` and so on — for the standard catalog and for the module's own primitives.

## 5. The server: the app API

### 5.1. Addresses

| Request | Response |
|---|---|
| `GET /app/{App}` | The manifest: the title, the menu, the screens with description hashes, the places, the language |
| `GET /app/{App}/screens/{Screen}.{hash}.json` | A screen description (§4.3) |
| `GET /app/{App}/{Screen}?parameters` | Screen data: the results of the nodes' queries, the computed `if`s, the available nodes (decision 5) |
| `GET /app/{App}/{Screen}/{place}?parameters&arguments` | A place query: the next page, filters, an `EntityPicker` search |
| `POST /app/{App}/{Screen}/{place}` | A place command (decision 6); the response is as from the model API (RFC §31.3) |
| `GET /app/{App}/openapi.json` | The app's contract |
| `GET /app/{App}/ws` | Notifications (§5.4) |
| `GET /ui/…` | The runtime: the built-in build or `ingress.ui.dir`; an unknown path gives `index.html` |

The module is `edge/appapi` (next to `edge/httpapi`, with shared authentication and the canonical JSON codec).

### 5.2. Loading screen data

1. Checking access to the app; the list of available nodes by the access of their methods.
2. The nodes' queries — along the tree, in one read snapshot; the arguments — from the screen parameters, `me` and the data of outer nodes by the links of the UI program. Independent queries run in parallel.
3. `if` — bytecode functions over the scopes' data; hidden nodes are not returned, and their nested queries do not run.
4. The response: the data by node number, the `if`s, the read position for `after` (RFC §31.3) — after a command the runtime rereads the screen with it.

### 5.3. Place operations

The place is looked up in the app's UI program; the place's method is called with the arguments from the body as an external call by the caller (RFC §19). Notifications to the initiator — in the response; errors — with a `path` for `invalidArgument`. A method that is not among the app's places cannot be called through the app API.

### 5.4. Notifications

`GET /app/{App}/ws` and long polling — on top of the existing delivery (`edge/httpapi/ws.go`); the token in a subprotocol (decision 11). Notifications to the recipient go to the runtime's `Toaster`; the errors and notifications of a step — in the operation's response.

### 5.5. Test mode

In `--test` the manifest marks the mode, and the runtime shows a "sign in as" panel; the session is an actor or a role and a tenant, the requests carry `Authorization: Test …`. The `--engine web` runner sets up the session itself (§7).

## 6. The web runtime and the standard catalog

### 6.1. The `web/` packages

| Package | What is in it |
|---|---|
| `@reasonr/runtime` | The manifest and screen descriptions, routes `/ui/{App}/{Screen}?parameters`, loading data, forms (values in the canonical JSON, field errors), events and navigation, rereading after a command, notifications, the labels of RFC §22.10, signing in (OIDC, `--test`), texts; the registry of primitive implementations |
| `@reasonr/std-ui` | The standard catalog's implementations on Ant Design |
| `@reasonr/vite` | The plugin: implementations from the module's `ui/web/`, a check against the `--ui-types` interfaces, a build into `dist` |

The runtime does not know the model: everything it needs is in the screen descriptions. Primitive implementations get ready props (RFC §22.7) and `rr` labels; in development mode the runtime checks that the labels are set.

### 6.2. The implementation registry

An implementation is looked up by the primitive's name: the module's own implementations → the standard catalog → the automatic UI. So the component library is swapped one primitive at a time (RFC §31.4), and one's own implementation of a standard primitive (`Table` on another library) replaces the catalog's without changing the layout.

### 6.3. Builds

- The built-in one (decision 8): the runtime + `std-ui`, `edge/webui/dist`, `make web`.
- One's own (decision 9): a project in the module's `ui/web/`; `ingress.ui.dir` points to the result.

## 7. UI tests: `--engine web`

```bash
reasonr test --engine web --url http://localhost:8080 examples/taxi   # reasonrd --test
reasonr test --engine web --coverage …                                # places no test reached
reasonr test --engine web --place Admin.AdminOrder:Order.Edit …       # only this place
reasonr test --engine web --navigate path …                           # to the screen — by clicks from the menu
```

The `web` driver (`testrun/web`, decision 12) implements `vm.Driver` by RFC §27.3:

| Section | How |
|---|---|
| `given`, `time passes`, system responses, new ids | Through the test API — like the `http` driver (its code is reused) |
| A command in `when` | Through a place: signing in as the caller, opening the screen (the parameters — from the step's arguments by the place's links; a place in a row — a search for `item:…:<id>` with paging), writing the arguments into the inputs, `submit:…`, waiting for the response, reading `error:*` and `notification:*` |
| A query in `then` | Through the query's place: opening the screen, filters, reading `result:…` (`data-rr-value`) |
| Notifications to other actors, external requests | Through the test API |

**Places and k runs.** The runner gets the places from the UI program. Before each step it finds the applicable places (access, visibility by the screen's data, the fixed values matching the step's arguments); the test runs k times — k is the maximum number of applicable places of one step — and in the i-th run the step takes the i-th place (round robin), each run in a new ephemeral tenant. No applicable place — a failure of kind `ui`: "the action is not available in the UI". The report is the same JSON format (`AGENTS.md`), with the place added to the step; a failure of kind `ui` comes with the element's label and a screenshot (`--artifacts`).

## 8. Taxi

## 10. Stages U1–U6

### U1. The language

- Syntax, the AST, `fmt` (§3.1); primitives and unification (§3.2); layout (§3.3); texts (§3.4); diagnostics (§3.5); `std/ui.rr`; removing the old syntax and `via`; the LSP, `explain`, `graph` (§3.6).
- Taxi: the model's additions, the apps, the admin, the texts (§8) — they compile; the scenario tests of the new commands pass in memory.
- **Done when:** negative tests for every diagnostic; taxi and every example compile; `fmt` is idempotent on layouts; a parser fuzz test with layouts.

### U2. The UI program

- The automatic UI and `reasonr ui eject` (§4.1); `reasonr.UI` (§4.2); `if` to bytecode; screen descriptions by language (§4.3); `reasonr build --ui-types` (§4.4).
- **Done when:** golden files of the taxi screen descriptions; `eject` of `app … auto` for taxi compiles and gives the same descriptions as `auto`; descriptions hold no names that are not on the screen.

### U3. The server

- `edge/appapi` (§5.1): the manifest, descriptions, screen data (§5.2), place operations (§5.3), the app's OpenAPI; WebSocket with a subprotocol (§5.4); test sign-in (§5.5); `ingress.ui`, C0014–C0016; serving the runtime.
- **Done when:** Go tests on memory and PostgreSQL: the admin's screen data for the roles `admin` and `support`; hidden nodes run no queries; a method outside the app's places cannot be called; notifications over WebSocket with the token in a subprotocol.

### U4. The web runtime and the catalog

- `@reasonr/runtime`, `@reasonr/std-ui` (Ant Design), `@reasonr/vite` (§6); the built-in build, `make web`, a check in CI; OIDC and sign-in in `--test`; the module's own implementations.
- **Done when:** every taxi screen opens in the built-in build and performs actions by hand; the runtime conformance suite (§11) passes; one's own `Table` implementation in a test module replaces the catalog's.

### U5. `--engine web`

- `testrun/web` (§7): `given` through the API, places and k runs, the failure kind `ui`, `--coverage`, `--place`, `--navigate path`, screenshots.
- **Done when:** the taxi tests pass `--engine web` on memory and PostgreSQL with the same report as `--engine http`; `--coverage` — every place of taxi is covered; a mutation (hiding a button with a wrong `if`) is caught by the failure "the action is not available in the UI".

### U6. Load and documentation

- The measurements of §12; the README "Interface" (apps, primitives, own implementations, signing in, `--engine web`); `AGENTS.md` (layout, binding rules, the E07xx diagnostics, UI tests); RFC §16; an `engine.yaml` example.
- **Done when:** the criteria of [§15](#15-acceptance-criteria) are met.

## 11. Testing

| Kind | What it checks | How |
|---|---|---|
| The compiler | Syntax, primitives, unification, binding, access, texts | Negative tests for every diagnostic, golden files of `fmt` and screen descriptions, parser fuzzing |
| The automatic UI | The rules of RFC §22.9 | Golden files of `eject` for taxi and small models |
| The server | Screen data, `if`, access, the place whitelist, WebSocket | Go tests of `edge/appapi`, `cmd/reasonrd/server` on memory and PostgreSQL |
| Runtime conformance | The runtime executes a screen description: binding, forms, navigation, labels | A set of screen descriptions with the expected behavior — Vitest + Testing Library; the same set — for the mobile runtime in stage 8 |
| The catalog | Implementations set labels, inputs return canonical values | Vitest in browser mode for every `std-ui` primitive |
| Scenarios through the browser | Logic + API + UI in every place | `reasonr test --engine web` on taxi, memory and PostgreSQL |

Every new test is checked by a mutation: the test must fail if what it checks is removed. Browser tests in CI are a separate job with a cache of the Playwright browsers; they are not part of the usual `make test`.

## 14. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Implicit binding is unpredictable for a product engineer | Medium | An ambiguity is an error with a fix; `explain` and the LSP hint show the source of every argument; golden tests of descriptions |
| Unifying type variables gives unclear errors | Medium | Messages in terms of the place ("the DriverInfo row has no field of type Customer.Id"), not of variables; negative tests for each |
| The standard catalog is not enough | High | The automatic UI in place of a missing primitive; the module's own primitives (decision 9) |
| The screen description — the contract for mobile — changes after U2 | Medium | A format version and the runtime conformance suite from U4 |
| Screen data is slow because of nested queries | Medium | Independent queries in parallel, one snapshot, hidden nodes do not run; the measurement of §12 |
| Fragile UI tests | Medium | Labels instead of selectors, waiting for the operation's response, screenshots; places and k runs give a reproducible order |
| Playwright is heavy for CI | Medium | A separate module and CI job, a browser cache |
| The built-in build diverges from the sources | Low | `make web` and a check in CI |

## 15. Acceptance criteria

1. The interface language of RFC §22 is implemented: the compiler, `fmt`, the LSP, `explain`, the E07xx and W13xx diagnostics with explanations; the old syntax is removed.
2. The taxi apps (passenger, driver, dispatcher, admin) work in the built-in build without TypeScript in the model: screens, forms, navigation, notifications, errors, signing in with `--test` and by OIDC; `app … auto` gives a working interface.
3. The app API: screen data in one request, operations only of the app's places, the app's OpenAPI.
4. The taxi scenario tests pass `--engine web` on memory and PostgreSQL with the same report as `--engine http`; `--coverage` — every place is covered.
5. The goals of §12 are met or the deviations are described in the progress.
6. The RFC is updated (§16); the README and `AGENTS.md` describe the interface and UI tests.

## 16. What changes in the RFC

After the decisions of §2 are approved:

- **§28.3:** the E07xx codes — the interface anew, W13xx — interface warnings; E0805 and W1011 are removed (decisions 1, 14).
- **§29:** the model's schema without `TypeApp`, `TypeScreen`, `TypePrimitive`; the UI program `reasonr.UI` next to the schema (decision 2).
- **§22.8:** the catalog is the file `std/ui.rr`, included implicitly (decision 3).
- **§31.4:** screen data in one request, `if` on the server (decisions 4, 5); the place whitelist (decision 6); a screen description in the user's language (decision 13); Ant Design is the library of the standard web catalog (decision 7).
- **§31.1:** `ingress[].ui` (`dir`, `auth.oidc`).
- **§33:** `reasonr build --ui-types`, `reasonr test --engine web --install`, `--artifacts`.
- **§38:** stage 6 — a reference to this plan.
