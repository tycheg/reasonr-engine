## Decisions made along the way

1. **The deadline timer is in the arguments, not a separate field.** The plan (§3.2) replaced `ExternalRequest.Timeout` with a `Timer` field. The `timeout` parameter stays an ordinary request parameter in the schema; `MethodInfo.TimeoutParam` is its number from 1, and `MethodInfo.Timeout(arena, arguments)` gets the timer. So the outbox, the delivery journal and the `then` checks do not change, and the timer is visible in `reasonr test -v` among the arguments. `ExternalRequest.Timeout` is removed; until the delivery queue (I2) requests are retried up to `dispatch.DefaultRequestTimeout` (1 h), and the `X-Reasonr-Timeout` header is no longer sent (`X-Reasonr-Deadline` — I3).
2. **Diagnostic codes E12xx** — a new range "External systems and fakes": E1201 (the system's role is one declared role), E1202 (the `timeout` parameter is not a timer), E1203 (the old form `timeout 30s`; the fix removes it and adds the parameter). W1030 — no public command is available to the system's role (a command without an access list is available to any role).
3. **A fake is members of the external system.** When the test program is built, `fake Matching` merges with a copy of `external Matching` (like `extend`): the system gets fields, events, commands and request implementations (`RequestDecl.Body`), and the schema gets an `ID` (uuid) and `MethodInfo.Fake` on the implemented requests. A fake has no separate type or name: `Matching.Setup(…)` in a test is a command of the system. There is one instance — `reasonr.FakeID(type)` (the zero uuid).
4. **The production and test programs.** `module.Program`/`compiler.Model` is the test one (with tests and fakes), `module.Production`/`compiler.ProductionModel` the production one. The production one is used by `reasonrd` without `--test`, `reasonr build` (the schema for `--against`, IR and bytecode), `reasonr engine check|build`, the `check --against` check; the test one by `reasonr check`, `reasonr test`, `explain`, `graph`, `pii`, the LSP, `reasonrd --test`. Before this, tests got into the production program too.
5. **Compatibility does not look inside external systems** (`compat`): `reasonrd --test` writes to the database the schema of the test program with the fakes' fields and events, and a production start after it must not consider them "removed". An external system keeps no model data. The test `compat.TestFakes`.
6. **A request implementation is a command of the system.** The function `Matching.findDriver` (`FuncCommand`) is tied to the request method; its parameters are all the request's parameters, `timeout` included (the engine passes the arguments whole), and the implementation's parameters take the slots of the same-named ones. The engine calls it as a command of the fake instance with `CallerFake` — an internal caller whose access is not checked.
7. **An API call from a fake is the effect `UnitOfWork.Calls`** (`reasonr.FakeCall`: the system, the entity, the id, the command, the arguments), the operation `callout` in the IR and the bytecode (`FormatVersion` 3). The calls go through the outbox (memory — `outboxEntry.unit.Calls`, PostgreSQL and MongoDB — the field `calls` of the `storekit` record), and the determinism check compares them. They hold no personal values (E1209 forbids `personal` in a fake), so they are not encrypted.
8. **The cascade** (`memory.Engine.cascade`, `testapi.API.cascade`): after a command and every timer the outbox is read after its own cursor; a request to a system with `MethodInfo.Fake` runs only if the fake instance exists in the store; the fake's calls are commands from `Caller{Kind: CallerUser, Roles: [the system's role]}`. More than `MaxCascade` (1000) units of work is a failure. Errors of the fake's commands — `memory.FakeError` → `vm.Step.FakeErrors` → a failure of kind `fake`; over HTTP — the field `fakeErrors` of the `/_test/{tenant}/captured` response. Notifications to the initiator of these commands are recorded with `To: none`.
9. **Part of I5 was done in I1:** without it the `ride.test.rr` scenarios would fail in the `TestScenarios` (PostgreSQL, MongoDB) and `TestScenariosHTTP*` suites. Done: the cascade in the test API (`POST /_test/{tenant}/fakes/{System}/{Command}`, the cascade in `captured` and after the timers of `clock`), the HTTP driver, storing fake rows (`TypeInfo.Stored`) and fake calls in the PostgreSQL and MongoDB outbox. Left for I5: the `fake` transport for the ordinary tenants of `reasonrd --test` through the delivery queue (I2).
10. **`fake` is a contextual keyword** (in RFC §6.4 — among the contextual ones): a declaration is recognized by `fake Name` at the start of a line, and a field or a variable `fake` is still allowed.
11. **Fake diagnostics:** E1204 — `fake` outside `*.fake.rr` of the base module; E1205 — not a fake in `*.fake.rr`; E1206 — no system with a role; a repeated fake — E0101; E1207 — the implementation does not repeat the request without `timeout`; E1208 — the command is not available to the system's role; E1209 — the fake reads the model or writes `personal`, `id`, `forget`; E1210 — `as` on a fake command. W1010 (a command without access) is not reported for fakes. The placement and system checks run when the module is loaded (once per module), the rest in sema; multi-file negative tests — `compiler/module/testdata/fakes`, `compiler/sema/testdata/fakes` (`TestModuleErrors`).
12. **The seed of the lowering fuzz test** is one file, so `*.fake.rr` and `ride.test.rr` are not in it.

Decisions 13–19 and 21 belong to the first version of I2 and are replaced by the plan's revision (§2.1); 20 (the order of requests is not kept) stays.

13. **The queue method names** — `EnqueueRequests`, `LeaseRequests`, `RequestDone`, `RetryRequest`, `BuryRequest`, `ReviveRequests`: the stores already implement `TimerSource` with `Lease`/`Retry`/`Dead`. `EnqueueRequests` takes the whole unit of work (the tenant, the position, the time, the key versions) and `only` — the request number for retrying a dead letter of the former stream. `RequestDone` without an outcome (in the plan — `Done(r, outcome)`): the outcome is a label of the metric `reasonr_requests_total{system, outcome}` (`delivered`, `retry`, `dead`, `expired`, `forgotten`), and the row is removed from the queue. The metric replaced `reasonr_requests_forgotten_total`; the latency "commit → delivery" — `reasonr_request_delivery_seconds{system}`.
14. **A repeated enqueue is filtered while the request is in the queue** (tenant, `Key`): a delivered one is deleted, so a repeat of the unit after a dispatcher failure may deliver it once more — the recipient filters by `Idempotency-Key`. Otherwise the queue would keep the keys of every request forever. A repeat does not reset the lease and the attempts (the check `RunRequests/Enqueue`).
15. **Encryption in the queue — by the resealer** (`Keyring.Resealer`) with the key versions of the unit from the outbox: a subject forgotten between the commit and the enqueue does not get a new key, and their argument is stored as `none`. For this `storekit.DecodePayload` and the in-memory outbox fill `ExternalRequest.Subjects`, as for events.
16. **The deadline timer is checked on lease** in the same query: PostgreSQL — a subquery to `rt_timers` in `returning`, MongoDB — one `find` by `_id $in`, memory — by the timer map. `LeasedRequest.Deadline` is the timer's moment (for `X-Reasonr-Deadline` in I3), `TimerGone` — the timer fired or was deleted. A dead timer counts as alive: the model has not reacted yet.
17. **`request_ttl` — only for requests without a deadline timer.** A request with a live timer is retried (a pause of 1, 2, 4… s, up to a minute) while the timer exists, even if its moment has passed and the timer has not run yet.
18. **Two time scales in `Sender`:** `Now` — leases and retry pauses (real time, shared by every tenant), `Clock` — the `request_ttl` deadline and the delivery latency from the unit's time (the engine clock; in test mode — the tenant's virtual clock).
19. **A pool without permanent goroutines:** a semaphore on `Workers`, leasing as many requests as there are free sends; with an empty queue — waiting for a `Wake` signal from this process's `requests` consumer or `Poll` (500 ms). There is no separate role: the sender works in the `dispatch` role. `Sender.SendDue` is one pass over the ready requests for tests (like `FireDue` for timers).
20. **The order of requests is not kept:** the stream by position used to deliver one entity's requests in order; now they go in parallel and are retried independently (decision 1). The integration service must not rely on order.
21. **The conformance model:** `Box.Ship` schedules a timer and sends `Store.ship(boxId, timeout)`.
22. **The transport gets the whole leased request:** `port.IntegrationTransport.Send(ctx, *LeasedRequest)` — the tenant, the request, the timer deadline (`Deadline`) and the attempt number (`Attempts`) for the headers `X-Reasonr-Deadline` and `X-Reasonr-Attempt`. The body is the arguments without the `timeout` parameter (`integration.Body`).
23. **The engine's JWT** — `auth.Signer` (ES256), in the engine through `port.RequestSigner` in `registry.Deps.Signer`. The configuration `integrations.auth: { key_file | key_env, kid, issuer, also }`. Differences from the plan:
    - `kid` defaults to the key thumbprint by RFC 7638;
    - `iss` is `issuer`, by default `reasonr`: the configuration has no "engine name" parameter;
    - `also` — additional public keys in the JWKS. Rotation: first the new key is published in `also`, then signing switches to it, and the old one stays in `also` until its tokens expire. Otherwise instances with different keys would serve different JWKS.

    The token lifetime is 5 min. `GET /.well-known/jwks.json` serves the JWKS on every HTTP ingress with `Cache-Control: max-age=300`. In `--test` a key is always created at start, even without `integrations`.
24. **The static token of the `http` transport is removed** (`token`, `token_env`): the engine's JWT replaces it, and C0012 requires a signing key. A configuration with the old key is the error "unknown key".
25. **`tenant.any`** (`auth: jwt`, `tenant: { claim, any }`). The tenant named by the `X-Reasonr-Tenant` header is passed to the authenticator in `port.Credentials.Tenant`; an ordinary token ignores this header. A token with the tenant `any` is checked against the model of the named tenant:
    - no header or an unknown tenant — 401;
    - the token has no roles, or has a role that does not belong to an external system of the model — 403 (a new reason `port.ErrForbidden`);
    - otherwise the caller is only the roles. The actor from the token is dropped, not forbidden, otherwise with `actor.type` without a claim (FixedActor) such a token would be impossible.
26. **The contract's OpenAPI** — `httpapi.IntegrationsOpenAPI`:
    - the operation `POST /requests/{System}/{request}` with a body without `timeout`;
    - the headers of §5.2; `X-Reasonr-Deadline` — only for requests with `timeout`;
    - the security scheme `engine`; `servers` — a variable for the service address; `components.schemas` holds only the schemas used;
    - the response commands — the extensions `x-reasonr-role` and `x-reasonr-replies`: operations of the model API whose access names the system's role explicitly. Commands with "any" access are not listed — they are available to everyone.

    Validation: `TestOpenAPIDump` (`REASONR_OPENAPI_DIR`) writes the contracts too, `npx @redocly/cli lint` — no errors, only the `info-license` warning, as for `/openapi.json`.
27. **C0010–C0012** are checked both in `reasonr engine check` and on every `reasonrd` command, including `migrate` and `requests retry`:
    - C0010 fires already, although the `fake` transport itself does not exist yet (I5);
    - C0012 — only outside `--test`;
    - C0011 — a warning on the `tenant.any` line.
28. **The contract Go test** `TestIntegrationsContract` (PostgreSQL, without Kafka; with Kafka — I5). The services `Matching` and `Payments` on `httptest`:
    - verify the engine's JWT by its JWKS and the headers;
    - answer with commands with a system JWT with the tenant `*` into the tenants `default` and `acme-prod`.

    `Payments` answers 503 while a ride in `default` waits for payment, and the matching request of `acme-prod` is delivered in ≤ 2 s meanwhile. After an engine restart the postponed payment request is delivered with the attempt count continued, and the order is paid.
29. **The I2 rework (§2.1 of the plan):**
    - **Writing on commit.** Requests are written to `rt_requests` by the commit transaction: memory — in `Commit` under the lock, PostgreSQL — in a batch after the outbox write, MongoDB — in the same transaction.
    - **Encryption before the key check.** The arguments are encrypted with the commit's key before the key check, so their keys are checked together with the rest.
    - **A repeated key is not written.** The request key is deterministic (the entity, the command, the time, the number), and for the recipient it is the same request. A repeat is filtered by `on conflict do nothing` in PostgreSQL, `$setOnInsert` in MongoDB (a duplicate error would abort the transaction) and skipping in memory. It occurs at equal times — in tests with a frozen clock.
    - **What is removed:** dead requests, `BuryRequest`, `ReviveRequests`, `EnqueueRequests`, the outbox consumer `requests`, `limits.request_ttl`, `reasonrd requests retry`, the `dead` column (the DDL migration drops it).
30. **Any response other than 2xx is a retry**, 4xx included: the service decides that a retry is useless. `port.ErrPermanent` from the transport now means "the request cannot be encoded" — such a request is dropped.
31. **The sender always runs** when the main store keeps requests, even without `integrations`. A request to a system without a transport is dropped right away, with the outcome `dropped` and a debug-level log line; C0004 warns about it at start. Otherwise requests would pile up in `rt_requests`.
32. **The sender wakes the kernel:** `kernel.Config.OnRequests` is called after the commit of a unit with requests. It wakes only the sender of its own process; an instance with only the `dispatch` role finds requests by polling every 500 ms. If that delay is a problem, `LISTEN/NOTIFY` can be added in PostgreSQL.
33. **Attempt outcomes** are the `outcome` label of the metric `reasonr_requests_total`: `delivered`, `retry`, `expired`, `forgotten`, `dropped`.
34. **The test API reads the outbox to the end** (`engine/testapi`, `pending`). Reading the outbox stops at positions whose transactions are still running, other tenants' included. So `captured` and the fake cascade, having read the outbox once, sometimes did not see their own commit — tests over HTTP failed occasionally (MongoDB — 4 of 50 already in I1). The sender in `--test` made it frequent on PostgreSQL. Now:
    - the test API remembers the position of the tenant's last known commit: from the `after` parameter of `captured` (`HTTPDriver` passes the position of the last command), from fakes and timers;
    - it reads the outbox up to it, waiting up to 10 s;
    - after the fix — 0 failures of 20 on memory, PostgreSQL and MongoDB.
35. **The bus reads the event store no further than the cursor of the `events` consumer** (`dispatch.Bus`). The `events` cursor moves only after the events of a unit are written. So the bus does not see a half-written unit: in MongoDB `InsertMany` runs without a transaction. The bus lags behind the event store by at most one batch; the `events` consumer wakes it (`Events.OnAppend`), and without a signal it polls every 500 ms.
36. **The bus cursor is the former `bus`, the lease is `dispatch:bus`.** The positions of the event store are outbox positions, so the cursor of the former `bus` consumer (publishing from the outbox) continues without publishing again. There is no `bus` consumer in the dispatcher any more. `reasonrd dispatch retry --consumer` names only `events`, `forget_log` and `projections:<store>`; `requests` was removed from the hint already in I2.
37. **A batch does not cut a unit of work:** `port.EventFeed.ReadEvents(after, upto, limit)` limits the number of events, not of units. If a batch is full, the events of its last position are put off until the next one. A unit larger than a batch is read whole by a separate query (`TestBusBatch`).
38. **A bus error is always a retry**; the bus has no dead letters: events with guarantees cannot be skipped. `port.ErrPermanent` (no topic, no permission, a record too large) changes only the log level — `error` instead of `warn` — and the metric `reasonr_bus_failures_total`. The pause is `dispatch.RetryPause` (1, 2, 4… s, up to a minute).
39. **The `ce_id` of a notification is `{tenant}/{position}/n{number}`** (a deviation from decision 12). The numbers of a unit's events and notifications are independent, and their `ce_source` may coincide (`reasonr/{tenant}/Customer`), so without the prefix the `ce_id` would repeat. The `Message.Type` of a notification is the type that declared it (`notification.Order`), not the recipient's type.
40. **Notifications — `dispatch.Notifier`, a queue in process memory** (10,000). `kernel.Config.Notify` gets every notification of a unit after commit — addressed ones and those to the initiator, including from migrations and timers. They are encoded right away, because the response arena gets released, and are queued without waiting. If the queue is full or the bus answered with an error, the notifications are lost (`reasonr_bus_dropped_total`). `Notifier` works with any role: notifications appear where commands run.
41. **Event arguments — as written in the event store**, without decoding by the schema. Otherwise an earlier event with a removed field would not read with the new schema. PostgreSQL returns `jsonb::text`: the field order is the `jsonb` order, not the schema's. Memory encodes by the tenant's schema.
42. **Kafka — franz-go v1.18.1** (`go 1.21`; v1.19 needs go 1.23.8, v1.20 — 1.24). The module `adapters/kafka` is part of the standard `reasonrd`. A missing topic on write is an error after one metadata retry (`UnknownTopicRetries(1)`), not after `timeout` expires.
43. **Checking topics at start:** a missing topic is a start error; an unavailable broker — a warning. The engine API does not depend on the bus, and messages wait for the broker. Checked are the event topics of every type with events and, with `notifications`, the notification topics of every tenant known at start. Extended by decision 55: creation by `create_topics`, `reasonrd topics`.
44. **The `kafka` request transport:**
    - writing to the topic `reasonr.request.{system}` (the `topic` template, also `{tenant}`), the record key is the idempotency key;
    - the format is CloudEvents, as on the bus: `ce_id` is the idempotency key, `ce_type` is `System.request`, the extensions `tenant`, `attempt`, `deadline`; the body is as over HTTP;
    - any write error is a retry by `integrations.retry`, a missing topic included: otherwise the sender would drop the request (`ErrPermanent` → `dropped`);
    - ~~the transport's topics are not checked at start: the factory does not know which systems it serves~~ — they are checked, decision 55.
45. **The `memory` bus** (`memory.Bus`) is registered in the build, like `log`: the reference of `RunPublisher` and the bus of tests. **C0006 is dropped**; `bus.publish` in the configuration is an error with a hint.
46. **Checks:**
    - `RunPublisher` (memory, Kafka): CloudEvents attributes, the key, the body, order by key, a retry with the same `ce_id`;
    - `RunUnitStore/EventFeed` (memory, PostgreSQL with and without RLS, MongoDB): tenants, positions, numbers, `limit`, `null` instead of personal values, a repeated write;
    - `RunPersonal/Bus` — personal arguments from the event store;
    - `TestBus*` and `TestNotifier` in `engine/dispatch`;
    - on Kafka — `TestUnavailable` (an unavailable broker and a missing topic: the cursor stays, after recovery everything is in key order), `TestTopics`, `TestRequests`;
    - `TestKafkaBus` in `reasonrd`: the topic check at start, the events and notifications of API commands.
47. **The `fake` transport — `testapi.Fakes`, which is also the outbox consumer `fakes`.**
    - `Send` runs the request implementation as a command of the fake instance (`CallerFake`). The command's idempotency key is the request key, so a repeated delivery does not run the fake twice.
    - The `fakes` consumer runs the fake's calls of model commands from the outbox on behalf of the system's role, with the key `fake/{position}/{number}`. Calls appear not only when a request runs: also from a fake command by its timer (`Payments.capture` after 5 s) and from `/_test/{tenant}/fakes`. So their source is the outbox, not the command's response in the transport.
    - The `fake` transport is registered in the build, like `http`. The factory needs the test API (`registry.Deps.Fakes`); without `--test` there is none, and the build fails (C0010).
48. **A request without an implementation in the fake, or to a fake not yet created, counts as delivered without running**, with an info-level log line — as in a test where such a request is "only recorded". There is no retry: otherwise a fake created later would run old requests. A rejected fake command, or a model command it called, is a warning in the log, without a retry.
49. **The transport and the consumer skip ephemeral tenants:** the test API's cascade runs their requests and calls synchronously at the end of a step (decision 8). `/_test/{tenant}/fakes` also accepts ordinary tenants: the command runs without a cascade, an unknown tenant is 404.
50. **The `timers` role in `--test` runs the timers of ordinary tenants** (a deviation from the earlier behavior: before, the role did not work in `--test` at all). Timers are selected per tenant that is not ephemeral, by the system clock. The timers of ephemeral tenants still fire only through `/_test/{tenant}/clock`, otherwise the role would claim them at the same time as the test API. Without this neither the payments fake's timer nor the deadlines of matching requests would fire for an ordinary tenant.
51. **The stream lease is released on stop:** the dispatcher and the bus call `Acquire` with a `ttl` of 0 on exit. The lease expires right away, and the call does not touch someone else's lease; no new port method is needed. Before, after a restart a new instance waited up to `LeaseTTL` (30 s) before continuing the projections, the event store and the bus. The Go test of §8 found this: an event written after a restart did not reach Kafka for 30 s. Checks — `TestRestart` and `TestBus` with a one-minute `LeaseTTL`.
52. **The Go test of §8 is `TestIntegrationsContract`, and with `REASONR_TEST_KAFKA` it also covers the bus** (`events: main`, `bus: kafka`, `notifications: true`). It checks:
    - the events of a `default` order in order, including those published after a restart; repeats are filtered by `ce_id`;
    - the notifications to the customer in both tenants;
    - `signedUp` with `phoneNumber: null` in both tenants.

    `reasonrd migrate` assembles the bus too and does not start without the topics, so the test creates the topics before the migration (the helper `kafkaTopics`).
53. **`TestFakeTransport`** (`reasonrd --test`, memory, `integrations: { default: { type: fake } }`):
    - a request to a fake not yet created gets no answer;
    - the fakes are set up through `/_test/default/fakes`;
    - a ride goes through matching, and after 5 s through charging by the fake's timer;
    - the taxi tests pass in ephemeral tenants on the same server.

    The unit check — `TestFakes` in `engine/testapi`: a repeated delivery and a repeated unit, skipping ephemeral tenants, a request without an implementation. `TestTestModeTimers` checks the timers of test mode.
54. **Checks by mutation:** for `Fakes` (ephemeral tenants in `Send` and `Deliver`, both idempotency keys, the system's role, a request without an implementation, a fake not yet created), for skipping ephemeral tenants in `FireDue` and for releasing the lease in the dispatcher and the bus every mutant is caught.
55. **Topics: checked at start, created in `migrate` by `create_topics`, listed by `reasonrd topics`.**
    - **Who builds the list.** The engine builds the list (`stateless.Topics`, `Engine.Topics`), not the adapter factory. The bus and the request transport implement `port.TopicBroker`: the name template, the `create_topics` settings, describing (the number of partitions) and creating topics. The factories no longer check anything. The transport needs the list of systems, which only the engine knows: the systems with their own entry in `integrations` and the rest through `default`. So the request topics are now checked too (decision 44 changed).
    - **When they are created.** `serve` only checks: a missing topic — a refusal with a hint about `reasonrd topics` and `create_topics` + `migrate`; an unavailable broker — a warning.
      - `migrate` creates missing topics only if the component has `create_topics: { partitions, replication, config }`. Zero or no value means the broker's default.
      - Existing topics are neither changed nor deleted. If the number of partitions differs from `create_topics`, a warning is reported.
      - A topic created at the same time by another instance is not an error.
      - `serve` with `create_topics` does not create topics: so a rollout with one `migrate` role does not depend on how many instances start.
    - **`--test` always creates them:** without `create_topics` — with one partition.
    - **`reasonrd topics --format text|json`** prints the list without connecting to the stores and the broker: franz-go clients connect lazily. The JSON has the component (`bus`, `integrations.<name>`) and the `create_topics` settings. The subcommand name differs from the options discussed (`migrate --dry-run`, `reasonr engine topics`): `migrate` also creates tables, and `reasonr` does not know the adapters of the built server.
    - **`migrate` and `serve` with a Kafka bus do not start without the topics.** The rollout order: `create_topics` + `migrate`, or topics created outside by `reasonrd topics`.
    - `DefaultRequestTopic` moved to `engine/bus` (`bus.RequestTopic`).
    - `RunIO` is `Run` with the subcommands' output in `stdout`.
    - Checks:
      - `TestTopics`, `TestTopicsList` (`engine/stateless`) — on a stub broker;
      - `TestTopics` (`adapters/kafka`) — partitions, the replication factor, `retention.ms`, a repeated creation, `create_topics` errors;
      - `TestKafkaBus` — the list, the refusal of `serve` and `migrate`, `serve` with `create_topics` does not create, `migrate` creates;
      - `TestKafkaTestModeTopics`;
      - every mutant is caught.
56. **`extend` of a projection is forbidden (E1010)** — the user's decision. The base model writes the row whole and would reset the tenant's fields, and partial writes by several authors need a version per field. A tenant keeps its own data in its own projection. Extensions (parameters of base commands, projections from an entity, projection fields of a tenant) are worked out in the multi-tenancy stage. The test data `compiler/module/testdata/ok` is without `extend OrderMart`; RFC §21.2.
57. **"Except fields with a default value" means optional (`T?`) fields and fields with an explicit `= value`.** By RFC §7.3 every field has a default value, and taken literally the requirement would be empty. The rule is the same as for a value object constructor (`required`). The error is a new **E0305**, not E0203: the explanation says why the row is written whole.
58. **Taxi:** `Order` keeps `driverName` and `driverPlate` from the event `driverAssigned` (`Driver.Accept` passes them as the arguments of `assignDriver`), and one command `Order.writeMart` writes the `OrderMart` row from the order's fields; the filling migration in RFC §32 calls it too. A deviation from the plan: "by one command" is read as one command called after every status change, not one write per order.
59. **Synchronous projections:** the row is written whole too, but the version is the former counter, and there are no deletion marks. The transaction with a row lock orders the writes, and in PostgreSQL the position of the unit is known only after the outbox write. The position-as-version and the marks belong to asynchronous projections (`ProjectionStore.Apply`).
60. **Deletion marks are kept apart from rows:** `rt_deleted` (the tenant, the type, the canonical JSON of the identifier, the deletion position) in PostgreSQL and MongoDB, a map in memory. Queries and unique indexes of projections do not change. A write with a greater version removes the mark.
61. **`Apply` no longer skips a position not greater than the applied one; `Applied` is the greatest applied position.** A repeat is safe by the row version. `after` stays exact while the dispatcher delivers positions in order, as now (the stream cursor); with out-of-order delivery `Applied` as "everything up to the position" would not work.
62. **Rows written before I7 move over without a migration:** their version is a write counter, which is not greater than the position of the last write, and the next position is greater than it.
63. **A unit's result for a row is its last operation** (`storekit.LastOps`) for synchronous and asynchronous projections: the row is written whole, the intermediate writes are not needed.
64. **Checks:** `RunProjectionStore/Apply` (a whole write, a repeat and a late position, an empty position, a deletion mark, a unit's last operation, tenants), `/Shuffled` (5 histories of 40 units over 4 rows, each unit 1–2 times, the order shuffled — the result is as in order), `RunUnitStore/Load` (a whole synchronous row, `Relabel`). The mutants are caught on three stores, except removing the mark on a new write in PostgreSQL: it is equivalent — a mark with a smaller version changes nothing.
65. **The event store is written in batches** (`dispatch.BatchConsumer`, `Events.DeliverBatch`): an outbox batch (up to 100 units) is one write to the store and one cursor move. Before, each unit took two writes to PostgreSQL in a row, and at ~1,200 commands/s the `events` consumer fell behind: the "commit → Kafka" latency grew with the length of the run (p50 15 s after 15 s of load). The write is idempotent (`on conflict do nothing`), so a batch is repeated whole on a failure; if a batch is not written, the dispatcher delivers it unit by unit, with retries and dead letters.
66. **The connection pool of the `http` transport:** as many idle connections per host as `integrations.workers` (`registry.Deps.Workers`). `http.DefaultTransport` has 2, and almost every one of 64 concurrent sends opened a new connection. With the pool the integration service does not lower command throughput (it was −8 %).
67. **Stopping the dispatcher does not log** a hundred "cursor not written" warnings with `context canceled`: the batch loop is interrupted.
68. **The measurement method.** `TestLoad`: 64 clients, 20 s, taxi over HTTP `--test`, PostgreSQL 17, Kafka (KRaft) — in Docker on the same machine (10 cores). The latency "commit → the request at the service" is counted from the start of the command that sent the request — an upper estimate (it includes the command itself and the asynchronous call `[order].finishRide`). The latency "commit → Kafka" — from `ce_time` (the unit's time) to receipt by the reader. `TestLoadRequests` — a queue of 50,000 requests built up by an instance with the `api` role and sent by an instance with the `dispatch` role; isolation — a stream of 200 commands/s with requests to two systems.
69. **A hung system is the integration service's concern** (the user's decision). The sends (`integrations.workers`) are shared by every system. A system that does not answer holds every attempt until the transport's `timeout` (10 s) and at 200 requests/s takes all 64 sends: in `TestLoadRequests/isolation/hang` the neighboring system got 192 of 1,994 requests delivered, p50 9.7 s. An immediate refusal (503, a refused connection) does not bother the neighbors. By the contract the integration service answers quickly (accepted — 2xx, runs it itself) and is available; the engine introduces no per-system send limit and no circuit breaker.

## Open questions

1. **Physically removing the deletion marks of asynchronous projections.** The apply order does not matter: a projection row has a version, and a write applies only if its version is greater than the stored one. So `delete [martId]` deletes the row and leaves a mark with the deletion version (`rt_deleted`): a write with a smaller version that comes later does not resurrect the row. When and how to remove the marks is open. Options:
   - cleaning marks older than a period after which there are no late writes;
   - cleaning after every position up to the deletion version has been processed.
