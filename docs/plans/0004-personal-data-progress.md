## Decisions made along the way

1. **Ports.** `port.KMS` (`Wrap`, `Unwrap` with a key context) and `port.KeyStore` (the tenant key; subject keys with versions) replaced the former `KeyStore` (`Key`, `Destroy`), which nobody implemented. A subject in the key store is a `port.SubjectRef`: the type name and the canonical JSON of the id, without an arena or a schema. Destroying a key is not a port method but part of `Commit` (`Work.Forget`); `pii.MemoryKeys` has a `Destroy` for this.
2. **A tombstone instead of deletion.** A destroyed key stays as a row without the key, with a version number: the subject's next key gets version +1 (decision 7), and old ciphertexts know their version is destroyed without asking "was there a key".
3. **The AAD of wrapping a subject key** is the tenant, the type and the id, without the version (§4.1 of the plan had the version): the store assigns the version on creation, and the wrapping happens before that. The version is part of the AAD of every value ciphertext.
4. **The key cache.** A cache entry with a version no lower than the ciphertext's is a final answer: the same version with a key — decrypt, a newer one or a tombstone — none; otherwise the key is reread. An older version does not replace a newer one in the cache. The absence of a key is not cached.
5. **HKDF** is our own (RFC 5869, checked against test vector 3): `crypto/hkdf` exists only from Go 1.24.
6. **The `local` KMS** reads the master key from `key`, `key_env` or `key_file` (base64, 32 bytes) and warns in the log outside `--test`.
7. **The label source.** The label of the `pii` analyzer is no longer a set of subject types but a set of sources: a subject and the path to its id in the fields of `self` (empty — `self` itself). In a command and a reaction a personal value comes only from a field or a parameter of `self`, so the path is always computable; a value from a record field (`c.phone` in a query) is marked foreign and gives no call site subjects — it only occurs in queries, which do not get into a unit of work.
8. **Where subjects are recorded.** `PIIMap.Sites` — for external requests, notifications and errors in commands and `on` reactions. Errors are now recorded in the flow map too (`reasonr pii`, kind `error`): they are not sinks, but they get into the retry response by key.
9. **The path to the VM.** `lower.Program` takes the whole `check.Result` (the searches and the `pii` map); `ir.Instr.Subjects` (the argument name, the type, a path by names) is printed in `--dump-ir`; codegen turns them into `bytecode.SiteSubject` (a parameter number, a `TypeRef`, a `FieldPath` from the function's owner type), and the disassembly prints them in `--dump-bytecode`. The VM computes the id from the snapshot of `self` at the moment of the call; a subject with a none id is skipped.
10. **E0906** — only for a subject path from a projection field; a path from `id` needs nothing, the operation always has `id`.
11. **A compiler bug found and fixed:** after `if note is not none` sema narrowed `note` to `string`, while lowering took the declared type `string?`, and the bytecode verifier rejected `"…" + note`. Now a field is read into a slot of the narrowed type, and a variable or a parameter is copied into it (`move`); the base of `rec.get`/`val.get` is not copied — these operations accept an optional record. The test is `runtime/vm/narrow_test.go`.
12. **A row's layout in memory.** A row keeps the state without personal values (none) — search and sorting run on it — the field ciphertexts (`storekit.Sealed`: the field number, the subjects, the data), the blind values of personal index keys with their subjects, and the list of subjects. The index `bySubject` (subject → rows) gives `forget` the rows without scanning the tenant. Events keep the same: arguments without personal values, and ciphertexts.
13. **A nested ciphertext.** For a value with data of several subjects (an argument of a request, a notification or an error) the ciphertext is encryption with each key in turn: forgetting any of them makes the value unreadable.
14. **A personal value without a subject** (a field `personal(customer)` with `customer` = none) is not stored under nobody's key: the commit is rejected with a failure (`storekit.ErrNoSubject`). Silently losing data is worse: the failure shows in the scenario tests.
15. **Encryption in memory happens inside `Commit` under the store lock,** like `forget`; so the key version check (decision 8) never fires in memory, but it runs — as for the other adapters. In the race "forget between execution and commit" the write gets a version conflict (forget incremented the row version), the kernel retries the command, and the new data goes under the key of the new version.
16. **Projections are decrypted before a partial upsert:** otherwise a personal field that was not passed would be lost when the row is encrypted again.
17. **The outbox in memory** keeps values without personal data and the ciphertexts; `Read` returns a decrypted copy in a new arena (a record without personal values — as before, without copying). If the tenant is deleted, personal values stay none.
18. **What stayed plain text in memory until P6:** the event journal `memory.Events` (a separate `EventSink` port), timer arguments, responses by idempotency key. The `RunPersonal` model does not use them; `Dump` already includes them, so P6 checks them with the same test. *P6:* all three are encrypted (decisions 36, 37, 41). The `ProjectionStore.Apply` port with `forget` — in P4 (in memory asynchronous projections are in the same `Store` and are erased by the `forget` commit).
19. **`RunPersonal`** (6 checks): storage without plain text (a store dump; a non-personal marker is in it — the dump is complete), search with `==` and `in` and uniqueness by a blind index, the outbox decrypted; `forget` erases the fields, the projection, the blind values, the outbox is unreadable, the number is released, the version grew; `forget` with an error deletes nothing; signing up again under a new key; tenants; a race of `forget` with a write. Mutations of the memory adapter (no encryption; not erasing blind values) are caught.
20. **The ciphertexts of a PostgreSQL row are in a `sealed jsonb` column,** not `{"$p": …}` inside `state` (decision 4 of the plan): every ciphertext has a field name, subjects and data. `state` is still read by the ordinary codec and by migrations, while `forget` and nested ciphertexts need the subjects. The column `subjects text[]` (`Type:id`) with a GIN index finds a subject's rows; blind key columns are `bytea` and are erased together with the ciphertext of their field.
21. **The outbox is shared by the stores:** `storekit.EncodePayload`/`DecodePayload` with `PayloadCrypto` write ciphertexts into the `sealed` field of events, projection operations and requests and decrypt them on reading (the keys in one query per record). A request parameter may be non-optional (`to string personal`), so the store codec has `jsonv.Codec.SealedPersonal`: a personal value is `null` even for a non-optional type.
22. **`reasonr.Event.Subjects`** — the subjects of an event's personal arguments; the store fills them when reading the outbox (consumers do not have the entity state from which `personal` paths are computed). The PostgreSQL event journal encrypts the arguments with them (`ev_events.sealed`), and the bus hides by them in P6.
23. **Keys in the commit transaction** are read and created through it (the transaction in the context of the `KeyStore` call), not through a second pool connection: with a busy pool commits would wait for each other. Unlike §4.1 of the plan, where the subject key is created outside the transaction: a created key rolls back with it, and after a failed commit the keys used are evicted from the cache. The tenant key is created before the transaction (`Sealer.Ready`): otherwise the cache could keep a key that is not in the database.
24. **The key check** (decision 8): a key created by this transaction (`pii.KeyVersion.Created`) is not checked — the insert lock holds the key row, and `forget` waits for the commit; the others — `for share` in one batch with the outbox write. Without this PostgreSQL lost 9 % of throughput (three extra round trips for `SignUp`).
25. **`ProjectionStore.Apply(…, forget port.Forget)`**: an asynchronous projection store erases subjects' data only in the rows of its own asynchronous projections (`Forget.Types` — from the consumer) and does not destroy keys. A refinement of §5 of the plan: in a database shared with the main store the key may by then have a new version (signing up again), and the rows of other types — data of the new version. For asynchronous projections in a separate database its subject key stays and the data is erased; a backup of such a database is covered by replaying the `forget` log (decision 13). Checked by `RunPersonal/ApplyForget`; `RunPersonal/Stored` also checks `Event.Subjects` in the outbox.
26. **KMS through the registry:** `registry.Deps.KMS` (from `crypto.kms`; in `--test` without `crypto` — `memory`) and `Deps.Keys` (the cache from `crypto.cache`). A store without a KMS works, and the first write of personal data fails with `pii.ErrNoKMS` (the C0007 check — P7). `port.Capabilities.Personal` is set for memory, PostgreSQL and MongoDB.
27. **An index on a personal field added to existing data** — `EnsureSchema` builds a blind column from the decrypted values (the test `TestMigrationsBlind`). A key column of the old type (plain text before P4) is a `SchemaError`: re-encryption is a P7 migration. The table `rt_forgotten` is no longer created; an existing one is not dropped.
28. **What stayed plain text in PostgreSQL until P6:** `rt_timers.args`, `rt_idempotency.result`, `rt_hub_payloads` (large notifications, temporarily). *P6:* encrypted (decisions 36, 37, 43). The `RunPersonal` model does not use them; the test dump covers every table of the schema, and P6 checks them with the same suite.
29. **A MongoDB document** is like a PostgreSQL row: `state` without personal values, `sealed` (the JSON of `storekit.EncodeSealed`), `_subj` — an array of "Type:id" with an index `{tenant, _subj}`, blind key fields — `BinData`. Keys: `rt_tenant_keys {_id: tenant}`, `rt_subject_keys {_id: {t, type, s}, v, wrapped}`; a destroyed key is a tombstone `wrapped: null` (decision 2), not a deleted document as in §7.3 of the plan. The collection `rt_forgotten` is no longer written.
30. **Touching the key document** (§7.3) is a batch of conditional updates `{_id, v, wrapped ≠ null}` → `seen`: a new `ObjectID`, not the outbox position: an update with the same value is not a write and gives no conflict, and with `Apply` the position may repeat. Fewer documents matched — `ErrConflict`.
31. **No check is needed if the document version does it.** A subject key is not touched if the unit of work replaced, with a version check, a document whose previous version held this subject's data (`findOneAndReplace` returns the previous `_subj` in the same round trip). `forget` of such a subject erases this document and increments its version: after it the replacement does not match the filter, concurrently with it — a write conflict; the encryption key is the same as for the previous data, because reading the document decrypted them and refreshed the cache. A refinement of decision 8 and §7.3 of the plan: only units of work that put a subject's data where it was not before write the key document (a new subject, foreign rows — projections, a subject's first data in a row, an instance with a stale cache). Without this MongoDB lost 10 % of throughput: `OrderTaxi` wrote its client's key document.
32. **A subject key on a cache miss — `CreateSubjectKey` right away** ("get or create"), without `SubjectKeys`: a miss on a write is almost always a new subject, and an existing subject's key is already in the cache (the command read their data). MongoDB — one pipeline update with upsert, no write for a live key (a repeated `_id` would abort the transaction); PostgreSQL — one statement with a CTE. A new subject costs one round trip instead of two in every store; the `port.KeyStore` contract is refined.
33. **MongoDB transaction attempts.** The driver retries the transaction function on a transient error; every attempt gets a new sealer, and the keys of the previous one are evicted from the cache: the ones created in it rolled back.
34. **`RunPersonal/StaleKey`** (`Stores.Twin` — a second instance of the store over the same data with its own key cache): another engine instance whose cache holds the key of a forgotten subject writes their data — the commit must notice the destroyed key. The mutations "no key check" on PostgreSQL and MongoDB and "the document's previous subjects taken from the new version" on MongoDB are caught; `Race` did not catch them: the row version check covers it. `storekit.Erase` and `storekit.Personal` — the imitation of `forget` before encryption — are removed.
35. **What stayed plain text in MongoDB until P6:** `rt_timers.args`, `rt_idempotency.result` — as in PostgreSQL (*P6:* encrypted, decisions 36, 37). An index on a personal field added to existing data is built from the decrypted values (`TestMigrationsBlind`). A key field that was plain text before P4 is replaced with a blind value by the recomputation (in PostgreSQL — a `SchemaError`, the column type differs); a `state` with plain text of such a field is re-encrypted by the P7 migration.
36. **Timer arguments.** The VM computes the subjects at `schedule` by the `personal` of the command's parameters from the snapshot of `self` — the entity the timer will call it on (`TimerOp.Subjects`; compared by the determinism check). The store keeps the arguments without personal values and the ciphertexts beside them: `rt_timers.sealed` (PostgreSQL), the `sealed` field (MongoDB), on the timer in memory; `Lease` decrypts. A personal argument without a subject is `ErrNoSubject`, as for fields (decision 14). The subject is forgotten before the timer fires: a non-optional argument is none, the kernel does not run the command, deletes the timer (a commit without `Work`) and writes an incident to the log and the metric `reasonr_timers_total{outcome="forgotten"}`; an optional one — the command gets none.
37. **Responses by idempotency key** (`storekit.EncodeResult`/`DecodeResult`, moved to `result.go`) encrypt the personal arguments of errors and notifications with the keys of their `Subjects`; a command retry after forget gets none in them. A response in memory is now stored as the same JSON as in PostgreSQL and MongoDB. Keys that only the response is encrypted with are not checked in commit (the check goes with the outbox): a key destroyed concurrently only makes the response unreadable, and leaves no data under the old key. The tenant key before the transaction (`Ready`) is now created for a rejected command with a retry key too.
38. **An external request after forget** (decision 11): the dispatcher does not send a request whose non-optional personal argument turned out none — a warning in the log and the metric `reasonr_requests_forgotten_total{system}`; no dead letter: a retry would not help, and the model sees the missing response through its timeout. An optional argument goes out as none.
39. **The bus** gets events with personal arguments as none and without `Event.Subjects` (by the `personal` of the event's parameters; a copy in the unit's arena).
40. **The forget log** (decision 13): the port `port.ForgetLog` (`Record`, `Forgotten(since)`), the effect stream consumer `dispatch.Forgets` ("forget_log"), the store from `crypto.forget_log`. Implementations: memory, PostgreSQL (`rt_forget_log`; a store without models creates the system tables too — the log is usually in a separate database), MongoDB (`rt_forget_log`, upsert). A record is the tenant, the position, the time of the unit of work, the subject (`port.SubjectRef`). `DropTenant` does not erase the log: it is an audit for `reasonrd pii replay` (P7). The effects of a deleted ephemeral tenant are not delivered, so in `reasonr test --engine http` the log is not always written — checked in `RunPersonal/ForgetLog`.
41. **The event journal in memory** encrypts personal arguments with the keys of `Event.Subjects`, like `ev_events` in PostgreSQL, and does not decrypt them; `Dump` includes the journal.
42. **Logs and traces** (decision 15): the arguments of commands and queries are not written to logs and trace attributes at all (the HTTP log — method, path, status, tenant, caller); the only place where a value got into an incident log — the failure message of `int`/`float`/`decimal` from a string — no longer contains the string. The `log` bus gets events already without personal arguments. A mask by schema will be needed once there are traces with attributes.
43. **Cache eviction over the hub** (§4.4): the ports `port.ForgetHub` (`PublishForgotten`, `OnForgotten`) and `port.KeyCache` (`DropKeys`). After a forget commit the kernel broadcasts the subjects through the hub (a hub error does not cancel the commit); the server subscribes every store with a key cache to the broadcast. The PostgreSQL hub — an `f:` message in the same NOTIFY channel (split under the limit), the in-memory hub — a call of the subscribers. A large notification in `rt_hub_payloads` is now encrypted with a random AES-256-GCM key, and the key goes only into the NOTIFY. Checked by `RunPersonal/Broadcast` (a second instance does not decrypt the outbox with the old key after the broadcast; without the broadcast it does).
44. **The `vault` KMS** — the package `edge/vault`: Transit over HTTP without an SDK, the key context is `associated_data` (the key `aes256-gcm96`; Vault 1.15+), `crypto.kms: { type: vault, address, key, token | token_env, mount, namespace, timeout }`. The test — `make vault-up`, `REASONR_TEST_VAULT`; the PostgreSQL and MongoDB HTTP scenarios ran with it.
45. **The compiler:** the result of `schedule` (a new `Timer.Id`) no longer inherits the label of the personal arguments of the timer's command — before, `let t = schedule(…, run: cmd(x: phone))` and writing `t` into a field gave a false E0901.
46. **The event journal and asynchronous projections in a separate database** encrypted with their own subject keys from their own database, and a forget in the main store did not destroy them. *Resolved (P7): the main store's keys* — decision 47.
47. **One set of keys for every store, and re-encryption with the outbox version.** Stores other than the main one get its `Keyring` when the engine is assembled (`pii.Shared`: `Keyring`, `UseKeyring`), so a forget makes the journal and the projections in a separate database unreadable too. The event journal and `Apply` re-encrypt data decrypted from the outbox, and on a cache miss they used to create a subject key. If a forget (or even signing up again) fell between reading the outbox and writing, the forgotten one's data went under a new key — in a shared database too. Now `Keyring.Resealer(tenant, keys)` is used: a value is encrypted only with the version from `CommittedUnit.Keys` (the one it was decrypted with from the outbox, `Sealer.Opened`) or the one the resealer itself decrypted the row's previous value with. The resealer creates neither subject nor tenant keys. No key, or a destroyed one — `pii.ErrKeyGone`, and the value is written as none, in the record itself, so no blind value is built either. The key check in `Apply` (`for share`, touching the key document) is removed: there are no new keys, and a version destroyed concurrently only makes what was written unreadable. Ports: `ProjectionStore.Apply(…, keys, forget)`, `CommittedUnit.Keys`, `port.KeyVersion`. So that reading the main store's keys does not get into the transaction of an additional store, the transaction key in the context of PostgreSQL is now per store, and MongoDB does not use another client's session for keys. Checks: `RunPersonal/Reseal` (after a forget and after signing up again the value and the blind value are not written), `RunPersonal/Separate` (a store in another database with a cold cache; without the context fix PostgreSQL does not find the key and MongoDB fails on a foreign session), `TestResealer`, `TestSharedKeyring`. A limitation: projections in a separate database written before P7 with its own keys cannot be read with the main keys (`ErrTampered`) — they need rebuilding.
48. **C0007–C0009** (`reasonr engine check` and the check at the start of `reasonrd`). They fire only if the models have personal fields or parameters:
    - **C0007** — no `crypto.kms`, except with `--test`.
    - **C0008** — a store does not encrypt personal data. It checks not only projections, as in §9 of the plan, but also `state` and an event journal with personal arguments: they hold them too. The property is declared by the store type at registration (`registry.RegisterStore(typ, f, registry.PersonalData)`; declared by memory, PostgreSQL and MongoDB). A type that is not in the build (for `reasonr engine check` without adapters) is not checked: a server built with the adapters checks it at start.
    - **C0009** (a warning) — `forget_log` is not set or equals `state`; not reported with `--test`.

    The examples `engine.example.yaml` and `engine.postgres.yaml` got `crypto` and a separate store `audit` for the forget log.

49. **`reasonrd pii rotate [--from <engine.yaml>]`** rewraps the tenant keys of the main store:
    - The port `port.TenantKeyRotator`: `TenantKeys` and `ReplaceTenantKey` with a check of the previous value.
    - `pii.Rotate` unwraps a key with the old master key (`crypto.kms` from `--from`; without the flag — the same KMS: a new Vault Transit key version), wraps it with the new one, checks that the new one unwraps it, and replaces it.
    - The tenant keys themselves do not change, so ciphertexts, blind indexes and the caches of running instances stay valid: rotation runs without a stop.
    - A retry after an interrupted rotation skips keys already rewrapped. A key that no master key unwraps stops the rotation.
    - Keys in the own tables of additional stores (before decision 47) are not rotated: they are no longer used.
50. **`reasonrd pii replay --since <backup time>`** — `Kernel.Forget`: a unit of work with only `UnitOfWork.Forget`.
    - It destroys keys and erases rows like a command's forget, with the outbox, retries on conflict and a broadcast through the hub.
    - Log records are taken no earlier than `--since`, without repeats, in batches of 100 subjects per tenant. Tenants not in the configuration are skipped.
    - It runs before the servers start.
    - A replayed forget goes into the log again (a new position): replaying again changes nothing.

    Checks:
    - `TestPIIReplay` — PostgreSQL: a real backup as a copy of the schema, the restore brought back the forgotten one's key, replay destroyed it and released the number;
    - `TestPIIRotate` — changing the local master key: a server with the new one fails before the rotation, works with the old data and its blind index after it, and fails with the old one;
    - `RunPersonal/Rotate` — three stores, a repeat is skipped;
    - `pii.TestRotate`.
51. **The migrations of §11** (PostgreSQL, MongoDB; memory keeps no data between runs).
    - **When.** Row storage is brought in line with the model after every new schema version and on the first start on data written before encryption. The marker is `resealed` on the version in `rt_schema_versions`; versions before P7 do not have it, so the first start scans every table with personal fields or ciphertexts once.
    - **Which rows are rewritten** (`storekit.NeedsReseal`):
      - `state` holds a value of a personal field: the field became `personal` or was written before encryption;
      - `sealed` holds a ciphertext of a field that is not `personal`, was renamed with `was`, or was removed.
    - **What is written.** The row is rewritten whole by the model: ciphertexts, `subjects`, blind keys. The row version grows, so a concurrent command gets a conflict. A value that stopped being `personal` is none for a forgotten subject.
    - **Batches.** PostgreSQL — 500 rows each, every batch in its own transaction with a key check. MongoDB — document by document, with a version check.
    - **A deviation from the plan: batch progress is not stored.** An interrupted migration rescans the table on a retry and skips the rows already done.
    - **A key column (PostgreSQL)** switching blind ↔ ordinary (by the previous schema from `rt_schema_versions`) is recreated together with its index and filled from the decrypted values.
    - **Three bugs found and fixed:**
      - `storekit` did not find the ciphertext of a renamed (`was`) field, while the AAD holds the old name: the value was silently lost. Now `Sealed.Member` is the name the value is encrypted under; the migration re-encrypts it under the new name.
      - An index on a renamed field stayed on the old column: in PostgreSQL `ensureIndex` compared only the index name, in MongoDB it failed on a definition conflict. Now both recreate the index.
      - The duplicate check of a unique index went through the pgx prepared statement cache and failed after a column type change.
    - **A limitation (migration).** A forget during the migration of a field that became `personal` does not find the rows with plain text yet (they have no `subjects`), and the migration encrypts them with a new key. Migrations are run before the servers start.
    - **A limitation (outbox).** Events in the outbox, timers and responses by key stay as they were.
    - **Checks:** `TestMigrationsPersonal` on PostgreSQL and MongoDB — became `personal`, renamed, stopped being `personal`, with a forget between the steps and a check of search and uniqueness after each step.
52. **`reasonrd pii reseal-events` is not done — a documented limitation** (the owner's decision). Events in the outbox and in the PostgreSQL and MongoDB event journal written before a parameter became `personal` stay plain text: they cannot be encrypted exactly, because the subject of a `personal(path)` parameter was computed from the entity state at the moment of the event, and the journal does not keep it. The limitation is described in RFC §32 and the README; if old events must be hidden, the journal is cleaned with database tools.
